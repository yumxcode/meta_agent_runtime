# Auto Scheduler

`auto + self_timer` uses durable suspension, not an in-process `sleep`.

## Lifecycle

1. A plain `auto` Agent calls `self_timer({ afterMs, reason, checkpoint? })`.
2. The Kernel commits the timer's `tool_result`, skips later calls in the same
   tool batch, flushes an Auto termination checkpoint, and returns `parked`.
3. The CLI atomically persists the complete session history.
4. Only after history is confirmed on disk does the CLI create a wake record at
   `<workspace>/.meta-agent/auto/wakes/`.
5. In the default detached mode, the current Auto process exits.
6. One `auto-scheduler` process claims due wakes and resumes the same session
   with the original goal, checkpoint, timer reason, and cumulative budget.

With `--attached`, step 5 changes: the CLI atomically leases the new wake before
publishing it, releases the model/router resources, and keeps only a lightweight
host alive. It renews the lease while waiting, resumes in the same terminal at
the deadline, and repeats if the Agent parks again.

Start the workspace scheduler:

```bash
meta-agent -w /path/to/project auto-scheduler
```

Or manage every discovered workspace from one terminal:

```bash
meta-agent tasks --manage --max-running 3
```

Managed mode opens the normal task TUI and also supplies the execution plane:

- due timers resume automatically; no separate `auto-scheduler` shell is needed;
- selecting a parked/overdue task and pressing `r` makes its wake due now;
- `--max-running` is one global limit across workspaces, not a per-workspace
  process limit; work beyond the limit remains queued;
- each turn runs in an exact one-shot scheduler worker, preserving the existing
  claim, lease, heartbeat, retry and resume-fence behaviour;
- provider profiles remain process-isolated and are restored from the wake.

The selected managed task's activity is shown in the lower half of the TUI.
Model replies are coalesced into readable paragraphs; tool calls/results,
retries, compaction, park, completion and failures are shown as separate event
rows. The panel follows the newest output automatically when the selection is
changed with `↑`/`↓`. A completed or newly-parked task keeps its most recent
turn visible while the manager remains open.

Workers still write independent, bounded-view NDJSON logs under
`$META_AGENT_HOME/managed-auto/logs/`; the TUI tails only the selected task's
log instead of piping child stdout into the terminal. This preserves detached
worker lifetime. If the TUI is closed and reopened while a managed worker is
still running, its scheduler heartbeat and wake id let the new TUI reattach to
the same log. A turn owned by an old standalone scheduler has no manager log
mapping, so the panel reports that live output is unavailable.

Leaving the TUI stops admission of new work. A worker already executing a turn
is detached from the terminal and finishes normally; a later timer remains in
the durable queue until managed mode or a workspace scheduler is started again.
For `--max-running` to be the machine's effective global limit, stop old
standalone `auto-scheduler` processes first; a scheduler outside the manager is
intentionally not killed or silently taken over.

Useful operator options:

```bash
meta-agent -w /path/to/project auto-scheduler \
  --poll-ms 1000 \
  --max-concurrent 1

# Claim and run currently-due work once, then exit.
meta-agent -w /path/to/project auto-scheduler --once
```

Keep one one-shot Auto run attached to its original terminal:

```bash
meta-agent -w /path/to/project --mode auto --attached \
  "持续检查构建状态；等待期间使用 self_timer"
```

`--attached` is valid only for a one-shot plain `auto` prompt. It is not an
interactive REPL and does not start a second daemon.

Global provider flags belong before `auto-scheduler`. API keys are never written
to wake files; provide them through the scheduler environment or global flags.

## Guarantees

- `self_timer` exists only in plain `auto`; `simple_auto` has no durable
  checkpoint and does not expose it.
- A timer is rejected while sub-agents are running or queued.
- Pending timers coalesce per session.
- Claims use a cross-process lock, owner token, TTL, heartbeat, and stale-claim
  recovery.
- Attached wake creation and initial claiming are one atomic store operation, so
  a workspace daemon cannot steal the wake between park and wait.
- `Ctrl+C` while the attached host is waiting releases the current lease back
  to `pending` and returns to the shell. The durable wake can then be recovered
  by `auto-scheduler`.
- `Ctrl+C` while an attached model turn is actively running means "abandon this
  Auto session": every wake for that session is cancelled and its checkpoint
  is marked `cancelled_by_user`, so a daemon cannot revive it. Workspace changes
  already made are not rolled back.
- `SIGTERM` remains recoverable, and a hard process crash is recovered after
  claim TTL expiry.
- A wake is cancelled as stale if the persisted history count, workspace, mode,
  or original goal no longer matches.
- A scheduler failure requeues the wake with exponential backoff.
- Cumulative spend is restored from the Auto checkpoint, so waking does not
  reset the session budget.
- Scheduler startup and idle polling are local filesystem operations; optional
  MCP connections are opened only after a due wake passes stale-state checks.

A standalone workspace scheduler is a long-lived host process (service,
launchd/systemd unit, tmux, or foreground command), not one process per timer.
Managed TUI mode instead uses exact one-shot workers so its parent can enforce a
single concurrency ceiling across workspaces.

## Seeing and steering tasks

```bash
meta-agent tasks
```

On a terminal this opens a full-screen view of every long-running Auto task; in
a pipe (or with `--json`) it prints one list and exits. Inspection needs no API
key. Managed workers use the same provider credentials as ordinary scheduler
runs and fail visibly if none are configured.

A task is a SESSION, not a wake — one task burns dozens of wakes over its life.
Each is classified from files that already exist:

| Status | Meaning |
|---|---|
| `running` | a claim is held and unexpired; a turn is executing |
| `parked` | a wake is scheduled in the future — the healthy waiting state |
| `overdue` | a wake came due and nothing claimed it (no scheduler, or it is wedged) |
| `stale-claim` | a claim outlived its lease; the executing process died |
| `orphaned` | the checkpoint says `parked` but NO wake exists — it will never resume |
| `finished` | nothing pending, nothing wrong |

`orphaned` is the one this view exists for. It is the state a session lands in
when its wake was cancelled or lost after parking, and until now nothing could
report it: the scheduler's own log reads `done` / `cancelled` / "no wakes left",
which is exactly what a clean finish looks like.

Workspaces are registered globally when an Auto wake is armed, so managed mode
can discover a first-time parked task without requiring a scheduler bootstrap.
Scheduler heartbeats remain the source of runner liveness.

Actions, from the TUI or the command line:

```bash
meta-agent tasks run-now <sessionId>          # bring a parked wake forward to now
meta-agent tasks cancel  <sessionId>          # drop a pending wake
meta-agent tasks kill    <sessionId> --yes    # interrupt the running turn
meta-agent tasks steer   <sessionId> "…"      # queue a mid-run correction
meta-agent tasks rm      <sessionId> --yes    # delete the task AND its history
```

Outside managed mode, actions only edit the durable queue. `run-now` moves
`fireAt` and lets a running workspace scheduler claim the wake on its next poll.
Inside `tasks --manage`, the TUI's `r` action also admits an exact worker, so it
works without a separately-running scheduler.

`cancel` and `kill` are separate verbs over the same store call because the
consequences differ: cancelling a pending wake is bookkeeping, while cancelling
a CLAIMED one makes the executing process lose its claim and abort the model
turn mid-flight. `rm` is irreversible — it removes the conversation history too,
so the session cannot be resumed afterwards.
