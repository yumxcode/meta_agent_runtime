## 0. 怎么读这份计划

- **阶段 1～2 是承诺项**，任务拆到可直接开工的粒度。
- **阶段 3～6 是规划项**，给出目标、前置条件、关键设计决策和验收标准，但**任务粒度会随前一阶段的真实结果调整**。把它们当作路线约束，不要当作已冻结的排期。
- 规模用 S / M / L 表示相对工作量（S ≈ 半天到一天，M ≈ 二到四天，L ≈ 一周以上），不是承诺工期。
- 每个阶段都有**中止条件**。中止条件触发时应停下来重新评估，而不是硬推到下一阶段。这比里程碑更重要。

### 通用工程约定

沿用仓库现有惯例，不新开范式：

| 事项 | 约定 |
| --- | --- |
| 模块布局 | 新子系统一个目录：`src/<name>/`，内含 `types.ts`（zod schema）、`<Name>Store.ts`、runner、`index.ts`、`__tests__/` |
| Schema | zod，`.strict()` 优先，跨进程产物一律带 `schemaVersion` 字面量 |
| 存储 | `metaAgentPath('<name>')`，目录 `0o700`、文件 `0o600`，`atomicWriteJson` + `withFileLock`，id 用正则守卫防路径穿越 |
| 幂等 | 内容稳定的指纹作 id；**任何进入人工决策的对象，其身份不得依赖会漂移的输入**（Reviewer 已踩过这个坑两次） |
| CLI | `meta-agent <name> <subcommand>`，在 `src/cli/args.ts` 注册名字、`src/cli/index.ts` 分发、`src/cli/commands/<name>.ts` 实现，支持 `--json` |
| 测试 | vitest，与被测模块同目录 `__tests__/`；**每个门槛、每个失败路径至少一个用例** |
| 脱敏 | 任何离开 canonical 的文本都要过 `redactSecrets` + 路径脱敏 |

## 1. 总览与依赖图

```text
阶段 1  数据资产化
  ├── 1A 回放评测集（EvalSet）        ← 提供 fitness function
  └── 1B 注入 provenance              ← 提供归因前提
            │
            ▼
阶段 2  L0 参数调优 + 失败模式聚类     ← 纯统计，验证数据质量
            │
            ▼
阶段 3  经验检索注入 + A/B 回放         ← 第一次真正闭环
            │
            ├──────────────┐
            ▼              ▼
阶段 4  L1/L2 演化      阶段 5  L3 路由 bandit
  prompt playbook          （可与阶段 4 并行）
  workflow 归纳
            │              │
            └──────┬───────┘
                   ▼
阶段 6  窄任务小模型 RL（可选）
```

**硬依赖**：阶段 3 之前必须完成 1A + 1B。没有评测集就无法证明注入有效，没有 provenance 就无法归因。这两条不能跳。

**软依赖**：阶段 4 与阶段 5 可并行，但共用评测集，需排队跑评测避免互相污染结论。

## 阶段 1：数据资产化

**目标**：把已有轨迹变成可度量、可归因的资产。本阶段**不改变任何 Agent 行为**。

### 1A 回放评测集（EvalSet）

#### 目标

固定一组任务用例，使得"换一套配置，跑同样的任务，比较结果"成为一个可重复的命令。

#### 关键设计决策

**决策 1：先做"重跑"，不做"精确回放"。**

精确回放（deterministic replay）需要 workspace 快照、外部 API 录制、时间冻结，工程量是重跑的数倍，且大量真实任务本质不可回放。第一版只做：固定初始 prompt + 固定 workspace git commit + 固定工具集 + 固定模型，重新真实执行，用**结果指标**比较。方差用重复次数处理，不用确定性处理。

`replayClass` 字段照记，但第一版只用它做**筛选**（`non_replayable` 不进 held-out），不用它驱动回放引擎。

**决策 2：用例来源优先"已有轨迹回捞"，而不是新写。**

从 TaskReview 里挑 `outcome.verdict` 明确、且证据链里有确定性验证（测试/构建/lint 通过或失败）的 TaskCase，把它的初始 prompt 和 workspace 状态提取出来。这样用例天然带"曾经的真实结果"作参照。

**决策 3：规模优先质量。20～50 个证据完整的用例即可起步。**

500 个残缺用例的价值低于 20 个完整用例——残缺用例会让指标失去区分度，比没有更糟。

#### 交付物

```text
src/evalset/
  types.ts            EvalCase / EvalSet / EvalRun / EvalResult 的 zod schema
  EvalSetStore.ts     metaAgentPath('evalset') 下的持久化
  CaseExtractor.ts    从 TaskReview + TaskCase 回捞候选用例
  EvalRunner.ts       批量执行 + 指标计算 + 配对比较
  metrics.ts          指标定义（单独文件，因为它是契约）
  index.ts
  __tests__/
src/cli/commands/evalset.ts
docs/知识系统/评测指标契约.md
```

#### Schema 草案

```ts
export const EvalCaseSchema = z.object({
  schemaVersion: z.literal('eval-case-1.0'),
  id: z.string().regex(/^evalcase_[a-f0-9]{24}$/),
  // 来源可追溯回原始轨迹，便于事后核对"当时到底发生了什么"
  origin: z.object({
    caseId: z.string(),
    rootTrajectoryId: z.string().uuid(),
    taskReviewId: z.string(),
  }).strict(),
  prompt: z.string().min(1),
  // SessionMode 全集含 campaign / robotics，但第一版评测集只收这三种：
  // campaign 跨度过长不适合重复执行，robotics 依赖真实硬件不可回放。
  mode: z.enum(['agentic', 'auto', 'simple_auto']),
  workspace: z.object({
    repo: z.string().optional(),
    commit: z.string().optional(),
    setupCommands: z.array(z.string()).max(8),
  }).strict(),
  successCriteria: z.array(z.object({
    id: z.string(),
    statement: z.string().min(1).max(1_000),
    // 关键：判定方式必须可执行，不能是"看起来对"
    check: z.discriminatedUnion('kind', [
      z.object({ kind: z.literal('command'), command: z.string(), expectExitCode: z.number().int() }),
      z.object({ kind: z.literal('file_exists'), path: z.string() }),
      z.object({ kind: z.literal('file_matches'), path: z.string(), pattern: z.string() }),
      z.object({ kind: z.literal('manual'), rubric: z.string() }),
    ]),
  })).min(1).max(20),
  replayClass: z.enum(['deterministic', 'approximate', 'non_replayable']),
  split: z.enum(['support', 'validation', 'held_out']),
  taskFamily: z.string().optional(),
  frozenAt: z.number(),
}).strict()
```

`check.kind === 'manual'` 的用例**不计入自动指标**，只作人工抽查。第一版应尽量避免 manual——如果一个用例的成功标准写不成可执行检查，它多半也不适合当评测用例。

#### 指标契约（冻结后不得改）

| 指标 | 定义 | 方向 |
| --- | --- | --- |
| `criteria_pass_rate` | 通过的 successCriteria 数 / 总数 | ↑ |
| `case_success_rate` | 全部 criteria 通过的用例比例 | ↑ |
| `false_success_rate` | Agent 宣称完成但 criteria 未全过的比例 | ↓ **核心反指标** |
| `repeat_pass_rate` | 同一用例重复 k 次全部通过的比例 | ↑ |
| `lower_tail_success` | 最差 task family cohort 的 case_success_rate | ↑ |
| `recovery_rate` | 出现工具错误后仍达成 criteria 的比例 | ↑ |
| `human_intervention_rate` | 触发人工 deny/redirect/steering 的用例比例 | ↓ |
| `cost_usd_per_success` | 总成本 / 成功用例数 | ↓ 约束 |
| `turns_per_success` | 总 turn / 成功用例数 | ↓ 约束 |

后两项是**约束不是目标**——单独优化它们会学到"少干活"。比较规则：硬约束（安全、false_success 不退化）+ Pareto 前沿，不压成单一标量。

#### 任务拆解

| # | 任务 | 规模 | 说明 |
| --- | --- | --- | --- |
| 1A-1 | 定义并冻结指标契约文档 | S | 先写文档再写代码，避免指标跟着实现漂 |
| 1A-2 | `types.ts` schema + 单测 | S | |
| 1A-3 | `EvalSetStore` 持久化 + 并发锁 + 单测 | S | 照搬 `ReviewerStore` 的模式 |
| 1A-4 | `CaseExtractor`：从 TaskReview 回捞候选 | M | 输出候选 + 缺失字段清单，**不自动定稿** |
| 1A-5 | `meta-agent evalset extract/list/show/freeze` CLI | M | freeze 是不可逆动作，需二次确认 |
| 1A-6 | `EvalRunner`：批量执行 + criteria 判定 + 指标计算 | L | 要处理超时、隔离 workspace、并发上限 |
| 1A-7 | 配对比较与报告（incumbent vs candidate） | M | 输出 markdown + json |
| 1A-8 | 人工定稿首批 20～50 个用例 | L | **这是人的工作，不是代码工作，别低估** |

#### 验收标准

- 同一配置连续跑两遍，`case_success_rate` 的差异可用重复次数解释（报告置信区间，不要求完全一致）；
- 用例的 split 切分无泄漏：同源任务及其改写不跨 split（用 `origin.caseId` + taskFamily 双重去重）；
- 指标计算有单测覆盖，包括 false_success 的判定逻辑；
- 至少 20 个 held-out 用例，其中 manual check 占比 < 20%；
- 冻结后的 EvalCase 内容 hash 稳定，改动需新版本号。

#### 中止条件

- 回捞发现**能提取出可执行 successCriteria 的 TaskCase 不足 15 个** → 说明轨迹的验收证据太弱，应先回到"让 Agent 产出可验证证据"这件事上，而不是硬凑评测集。

### 1B 注入 provenance

#### 目标

让轨迹能回答："这次运行注入了哪些经验/上下文条目，版本是什么，为什么选它。"

#### 现状与缺口

已有：
- `knowledge` item 有 `kind` / `action` / `entryIds` / `query` / `operation`，且是 `.passthrough()`；
- robotics 的 `experience_load` / `experience_search` / `principle_load` 工具在**被显式调用时**会发射 `action: 'recalled'`；
- `ExperienceWorkingSet` 内部已有 `injectedIds` 概念。

缺口：
1. **`recalled` ≠ `injected`**。检索到 10 条、实际进 prompt 3 条，现在只记了检索。归因需要的是后者。
2. **自动注入不发射**。`ExperienceWorkingSet` 的自动预载没有对应的 trajectory item。
3. **没有版本**。`entryIds` 没有内容版本，条目改写后无法区分。

#### 设计

扩展 `KnowledgeItemSchema`（passthrough 已允许，但要显式化并加校验）：

```ts
action: z.enum([
  'recalled', 'proposed', 'approved', 'rejected', 'written', 'deleted',
  'injected',                      // 新增：确实进入了本轮上下文
]),
// 新增字段
injected: z.array(z.object({
  entryId: z.string(),
  contentHash: z.string().regex(/^[a-f0-9]{64}$/),
  source: z.enum(['experience_store', 'reviewer_candidate', 'workflow', 'playbook']),
  selectedBy: z.enum(['explicit_tool', 'auto_working_set', 'always_on']),
  reason: z.string().max(500).optional(),
})).max(32).optional(),
tokenCost: z.number().int().nonnegative().optional(),
```

**同时记录未被选中但可召回的候选**（`ExperienceWorkingSet` 已有这个信息），这是后续做反事实消融的原料。

#### 任务拆解

| # | 任务 | 规模 |
| --- | --- | --- |
| 1B-1 | 扩展 `KnowledgeItemSchema`，加 `injected` action 与字段 + schema 单测 | S |
| 1B-2 | `ExperienceWorkingSet` 在实际注入时发射 knowledge item | M |
| 1B-3 | 显式工具（`experience_load` 等）区分 recalled / injected | S |
| 1B-4 | `contentHash` 计算与 `ExperienceStore` 打通 | M |
| 1B-5 | TaskCase / TaskReview 汇总本次注入集合，写进 TaskReview | M |
| 1B-6 | 事件契约版本号处理（若涉及 KernelEvent 则走 1.2.0 → 1.3.0 流程，含 fixture + 指纹） | S |

#### 验收标准

- 一次带自动注入的 auto 运行，轨迹里能查到 `action: 'injected'` 的 knowledge item，且 `entryId + contentHash` 与 ExperienceStore 里的条目对得上；
- 检索到但未注入的候选可被区分；
- TaskReview 能列出"本次注入集合"；
- 无注入时不产生噪音 item（不要每轮都写空记录）。

#### 中止条件

无。这是纯增量记录，风险最低，**应当最先做**——因为阶段 3 之后再补就已经晚了，那时的历史轨迹已经无法归因。

## 阶段 2：L0 参数调优 + 失败模式聚类

**目标**：不训练任何模型，用统计把已有参数调对；同时验证数据质量是否支撑更上层的优化。

### 2A L0 参数调优

候选参数与对应的证据来源：

| 参数 | 证据 | 分析方法 |
| --- | --- | --- |
| `maxVerifyRounds` | `evaluation`（auto_verify 的 round + verdict） | 通过轮次分布；找边际收益归零的拐点 |
| compaction 触发点 | `compaction` item 的 previous/summary tokens + 之后的成功率 | 比较不同触发点后的 goal drift 与恢复轮数 |
| 重试退避策略 | 重复失败签名的间隔分布 | 复现间隔 vs 最终恢复率 |
| 子代理拆分阈值 | `subagent` item + 任务规模 + 结果 | 拆分度 vs 成功率/成本 |
| 工具超时 | `tool_outcome.durationMs` 分布 | 分位数；超时截断损失了多少本会成功的调用 |
| 并发上限 | 并发数 vs 错误率/合并冲突 | |

**方法**：先做描述性统计和相关性，**得出的每一条改动都要在阶段 1A 的评测集上验证**，不要直接改默认值。

### 2B 失败模式聚类

输入：TaskReview 的 Finding + 失败签名 + `run_result.outcome` + 人工纠正点。

输出：按机制归类的失败簇（对应自进化方案 §5.5 的 failure taxonomy），每簇带样本数、代表性证据 ordinal、可能受影响的机制。

**这一步的产物直接决定阶段 3～5 该优先改什么。** 也顺便解决"人工标注稀疏"的问题——让人审的是分类好的失败簇，不是逐条独立提案。

### 任务拆解

| # | 任务 | 规模 |
| --- | --- | --- |
| 2-1 | 轨迹统计导出工具（`meta-agent trajectory stats --json`） | M |
| 2-2 | 六类参数的分析脚本 + 结论文档 | L |
| 2-3 | 失败簇聚类（先用确定性特征，不急着上 embedding） | M |
| 2-4 | 每条参数改动在评测集上做配对验证 | M |
| 2-5 | 冻结新默认值 + 回归测试 | S |

### 验收标准

- 至少 3 个参数有证据支持的调整建议，且在 held-out 上不使 `false_success_rate` 退化；
- 失败簇覆盖 ≥ 70% 的失败样本，剩余进 `unknown`（**不允许强行归类**）；
- 分析可重跑：同样的轨迹输入得到同样的结论。

### 中止条件

- **参数分析得不出任何可信结论** → 数据量或数据质量不足，回到阶段 1 补数据，不要进阶段 3。这是本计划里最重要的一个 gate。

## 阶段 3：经验检索注入 + A/B 回放

**目标**：第一次真正闭环——Reviewer 产出的经验进入 Agent 上下文，并用评测集证明它有没有用。

### 前置条件（硬）

- 1A 评测集已冻结，1B provenance 已上线；
- 阶段 2 的失败簇给出了"哪类问题值得用经验解决"。

### 关键设计决策

**决策 1：注入的是 ExperienceCandidate，不是 ExperienceEntry。**

按 Reviewer 设计 §12.2，Candidate → 正式知识系统还需要第二道编译与审批。阶段 3 走独立的注入通道，不污染正式 ExperienceStore。

**决策 2：先做规则检索，不做语义检索。**

`ExperienceCandidate.applicability.cues` 已经是结构化触发信号。先用 cue 匹配 + taskFamily 过滤，跑通闭环再考虑 embedding。语义检索会引入一个新的、不可解释的失败源。

**决策 3：注入必须可关闭，且默认关闭。**

用开关控制，A/B 两组配置只差这一个开关。

### 任务拆解

| # | 任务 | 规模 |
| --- | --- | --- |
| 3-1 | Candidate 检索器（cue 匹配 + 边界排除 + 打分） | M |
| 3-2 | 注入点与 token 预算控制 | M |
| 3-3 | 注入开关 + 配置项 | S |
| 3-4 | A/B 评测：开关 on/off 各跑 k 次，配对比较 | M |
| 3-5 | 单条经验的边际价值分析（用 provenance 做归因） | M |
| 3-6 | 失效经验的降权/淘汰机制 | M |

### 验收标准

- A/B 在 held-out 上有统计可辨的差异（正负都算有效结论）；
- 能回答"哪几条经验实际有贡献"——这依赖 1B 的 provenance；
- `false_success_rate` 不退化；context token 增量在预算内；
- 注入关闭时行为与基线完全一致（无副作用）。

### 中止条件

- **注入后 held-out 无改善甚至退化，且归因显示经验条目本身质量不足** → 回到 Reviewer 的质量门槛，而不是加大注入量或放宽门槛。这是最容易走错的岔路。

## 阶段 4：L1/L2 演化（prompt playbook + workflow 归纳）

**目标**：把上下文和流程本身变成被优化的对象。

### 4A ACE 式增量 playbook

把注入的经验集合组织成**不断累积的 playbook**而非压缩摘要：Generator（Worker 产生轨迹）/ Reflector（Learning Reviewer 提炼）/ Curator（新增，负责增量合并与组织）。

关键是 Curator 必须**增量更新**：新增条目、收窄适用边界、降低置信、标记 superseded，**不在原位重写整个 playbook**——那正是 context collapse 的成因。

### 4B GEPA 式反射演化

对系统提示的各 section 做反射式演化：采样轨迹 → 自然语言诊断 → 提出变更 → 在评测集上测试 → Pareto 前沿保留。

**前置**：评测集必须已经稳定，否则演化会拟合评测噪音。

### 4C AWM 式 workflow 归纳

从成功轨迹归纳可复用多步流程，存为结构化 workflow，按情境检索注入。`phase` item 与 TaskReview 的路径重建是输入。

### 验收标准（规划级）

- playbook 增量更新后，历史条目不丢失（有版本链可查）；
- prompt 演化的每个候选都有 held-out 配对结果和 rollback target；
- 演化产物不得由被评 Agent 自行晋升（治理见自进化方案 §10）。

### 中止条件

- 演化候选在 held-out 上的提升无法与重复运行的方差区分 → 评测集区分度不足，回阶段 1A 扩充用例。

---

## 阶段 5：L3 路由 contextual bandit

**目标**：模型选择、子代理拆分、工具选择、预算分配的策略化。

### 关键设计决策

**先离线反事实评估（IPS / doubly robust），再灰度。** 历史轨迹里有大量"选了 A 的结果"，但没有"选 B 会怎样"。直接上线学习会在真实用户任务上试错，代价不可接受。

**bandit 只在可行域内选择。** 安全约束、预算上限、权限策略是硬边界，由 L0 管理，bandit 不得触碰。

### 前置条件

- 需要 turn / decision 级 episode（自进化方案 §7.1 的待建粒度）——**这是阶段 5 才需要建设的，不要提前做**；
- 阶段 1A 评测集需扩充到能区分路由差异的规模。

### 验收标准（规划级）

- 离线反事实估计与线上灰度结果方向一致；
- 跨模型方差不上升（防止过拟合到单一 provider）；
- 可一键回退到固定路由。

---

## 阶段 6：窄任务小模型 RL（可选）

**目标**：在明确受限的窄任务上引入 open-weight 模型并做权重训练。

### 候选窄任务

优先级从高到低：compaction 摘要 → 失败分诊 → verify judge → 经验条目改写。

选择标准：任务边界清晰、有可验证 reward、失败可回退到当前实现、不直接触碰用户工作区。

### 前置条件（全部满足才启动）

1. 阶段 1～4 已完成，评测集稳定且有区分度；
2. 可验证 reward 链路成熟（确定性检查覆盖率足够）；
3. 已确认该窄任务用 L0～L3 手段无法进一步改善；
4. 接受"引入 open-weight 底座"带来的部署与运维成本。

### 参考形态

EvolveR 的三段闭环：离线自蒸馏（冻结策略，把轨迹蒸馏为抽象原则库）→ 在线交互（用原则指导决策）→ 策略进化（RL 更新，闭合循环）。

### 强制约束

- **reward 只能来自确定性信号**，LLM judge 只做 tie-break；
- 训练数据必须遵守 `trainingEligibility` 与 workspace 隔离；
- 必须保留非训练版本作为随时可切回的对照；
- 被训练模型不得参与自己的评测。

### 中止条件

- 出现 reward hacking 迹象（judge 分数上升但 held-out 准确率停滞/下降、输出出现异常模式）→ **立即停止训练并回滚**，不要试图"再加一点正则"。

## 7. 跨阶段风险与应对

| 风险 | 触发信号 | 应对 |
| --- | --- | --- |
| 评测集拟合 | 候选在 held-out 上持续提升，真实用户任务无感 | 定期换血 held-out；引入时间切分（新任务只进 held-out） |
| 分布偏移 | 优化后对新类型任务表现下降 | 保留 incumbent 对照；`lower_tail_success` 作硬门槛 |
| 归因失效 | 无法解释某次提升来自什么 | 阶段 1B 的 provenance；缺失时不得声称因果 |
| 幸存者偏差 | 失败样本轨迹残缺 | 用 `run_result.outcome` 识别非正常终止；残缺样本只进 support |
| 自评污染 | 有人拿 TaskReview 四维评分当指标 | 见自进化方案 §8.5，这是硬性禁令 |
| 阶段跳跃 | 跳过阶段 2 直接做注入或演化 | 阶段 2 的中止条件是全局 gate |
| 治理绕过 | 候选自行晋升、修改 evaluator | 自进化方案 §10 / §13 的门槛不因进度压力放宽 |

## 8. 里程碑总表

| 里程碑 | 内容 | 完成判据 | 依赖 |
| --- | --- | --- | --- |
| **M1** | 1B provenance 上线 | 注入可查、可对账 | 无 |
| **M2** | 1A 评测集冻结 | ≥ 20 个 held-out 用例，指标契约冻结，重复运行方差可解释 | 无 |
| **M3** | 阶段 2 完成 | ≥ 3 个参数有证据支持的调整；失败簇覆盖 ≥ 70% | M2 |
| **M4** | 阶段 3 闭环 | A/B 有统计可辨结论；单条经验边际价值可归因 | M1 + M2 + M3 |
| **M5** | 阶段 4 首个演化候选晋升 | 有 held-out 配对结果 + rollback target | M4 |
| **M6** | 阶段 5 路由策略灰度 | 离线估计与灰度方向一致 | M4 |
| **M7** | 阶段 6 决策点 | 前置四条全部满足才启动；否则明确记录"暂不启动" | M5 + M6 |

**M1 和 M2 可并行，且应当立刻开始。** M1 尤其紧急——它是纯增量记录，但一旦阶段 3 开始而它还没上线，那段时间的轨迹将永久失去归因能力。

## 9. 与现有迭代计划的关系

本计划属于[`meta-agent-自进化方案.md`](../reviews/meta-agent-自进化方案.md) §3.2 定义的 evolution track，与 A3-M5 的可信切读发布互不阻塞，共用 A3 的身份、ordinal、父子关系、证据和隐私契约。

本计划的阶段 1～2 对应自进化方案 §15 实施顺序的第 3～5 步；阶段 3～4 对应其第 7～9 步的机制候选。治理门槛（评测独立性、shadow → canary → promotion、回滚一等）全程以自进化方案 §10 / §13 为准，本计划不重复定义。
