## 0. 怎么读这份计划

v1 按"六阶段"排，把 Experience 注入放在第 3 阶段、把 P0 可靠性机制放在其后，并且默认单一 `held_out` 可以反复使用。审查判定这是**优化目标漂移 + 测试集独立性失效**，本版按 G0～G7 重排。

- **G0～G1 是承诺项**，任务拆到可开工粒度。
- **G2 是 Conditional Go**，仅限只读分析，不得改变生产行为。
- **G3 及之后是规划项**，给目标、前置条件与放行门槛；任务粒度随前一 gate 的真实结果确定。
- 规模用 S / M / L 表示相对工作量（S ≈ 半天到一天，M ≈ 二到四天，L ≈ 一周以上），不是承诺工期。
- 每个 gate 有**中止条件**。中止条件比里程碑重要：触发时停下重估，而不是硬推。
- **不设产出配额。** "完成 N 个参数调整""失败簇覆盖 X%"不再是成功标准——能有充分证据地得出"当前不应改"同样是成功。

### 通用工程约定

| 事项 | 约定 |
| --- | --- |
| 模块布局 | 一个子系统一个目录：`src/<name>/`，内含 `types.ts`（zod）、`<Name>Store.ts`、runner、`index.ts`、`__tests__/` |
| Schema | zod，`.strict()` 优先，跨进程产物一律带 `schemaVersion` 字面量 |
| 存储 | `metaAgentPath('<name>')`，目录 `0o700` / 文件 `0o600`，`atomicWriteJson` + `withFileLock`，id 用正则守卫防路径穿越 |
| 幂等 | 内容稳定的指纹作 id；**进入人工决策的对象，其身份不得依赖会漂移的输入**（Reviewer 已在此踩坑两次） |
| CLI | `meta-agent <name> <sub>`，`src/cli/args.ts` 注册、`src/cli/index.ts` 分发、`src/cli/commands/<name>.ts` 实现，支持 `--json` |
| 测试 | vitest，同目录 `__tests__/`；**每个门槛、每条失败路径至少一个用例** |
| 脱敏 | 任何离开 canonical 的文本过 `redactSecrets` + 路径脱敏；导出物二次脱敏 |
| Fail closed | 资格缺失、边界未知、证据不足一律拒绝，不做乐观默认 |

## 1. 七个 gate 与依赖

```text
G0  信任与数据契约
    eligibility · evaluator 分级 · artifact registry · experiment manifest · 注入 provenance
                          │
                          ▼
G1  受控重执行评测底座
    base snapshot · 隔离 runner · support/validation/sealed/canary · 指标与统计契约
                          │
                          ▼
G2  只读 Shadow + L0（Conditional Go）
    数据质量审计 · 描述统计 · failure taxonomy · 参数候选（不直接改默认值）
                          │
                          ▼
G3  Task Contract + Verifier          ← 先建"什么算完成"的信任底座
                          │
                          ▼
G4  State + Context + Recovery
                          │
                          ▼
G5  Experience / playbook / workflow  ← 只处理失败簇证明适合外置知识解决的问题
                          │
                          ▼
G6  Routing bandit（需先有随机 logging policy 与支持覆盖）
                          │
                          ▼
G7  窄任务权重训练（可选，重新立项）
```

**与 v1 的三个关键差异**：

1. 数据资格、evaluator bundle、artifact registry、experiment manifest 与 provenance 并列为 G0 硬依赖，不再是"后续建设"。
2. 两个 P0 可靠性机制实验（G3 / G4）前移到 Experience 注入（G5）之前。
3. `held_out` 拆成 support / validation / sealed test / canary 四层，可见性与使用次数分别约束。

## G0：信任与数据契约

**目标**：让"哪些数据可用、谁的判定可信、候选面能否还原、注入了什么"四件事有可执行答案。本 gate **不改变任何 Agent 行为**。

### G0 的范围锚点（防止镀金）

G0 极易膨胀成一整套没有反馈信号的基础设施，最后造出没人用的注册表。

> **锚点：G0 只做"跑通 G1 那个合成 fixture 端到端所必需的最小集"。** 超出这个范围的字段、后台、查询能力一律推迟到有真实调用方时再加。

判据很具体：如果一个字段在 G1 的合成 fixture 全链路里不会被读取，它就不属于 G0。

### G0-A 数据资格闸门

`可审计` ≠ `可用于学习或重复执行`。任何 TaskCase 进入 support / validation / sealed test 前必须有资格判定，**默认 `denied`**。

```ts
export const DataEligibilitySchema = z.object({
  schemaVersion: z.literal('data-eligibility-1.0'),
  subjectRef: z.string(),                       // caseId 或 trajectoryId
  trainingEligibility: z.enum(['denied', 'local_only', 'workspace', 'aggregate']),
  workspaceId: z.string().optional(),
  dataSubject: z.string().optional(),
  retentionUntil: z.number().optional(),
  allowedUses: z.array(z.enum(['audit', 'analysis', 'evaluation', 'candidate_generation', 'training'])),
  crossWorkspace: z.literal(false).or(z.object({ approvedBy: z.string(), approvedAt: z.number() }).strict()),
  decidedAt: z.number(),
}).strict()
```

缺失资格时 fail closed —— 不是"默认允许本地使用"。

### G0-B Evaluator 信任分级

给每个判定来源打等级，杜绝"因为 item 类型叫 `evaluation` 就当成 reward"：

| 等级 | 含义 | 可用作 | 当前实例 |
| --- | --- | --- | --- |
| T0 | executor 自报 | 仅展示 | 最终助手消息、`run_result` |
| T1 | 隔离上下文 LLM judge | critique、过程弱信号、人工导航 | **`auto_verify`** |
| T2 | 独立进程的确定性检查 | 主要自动指标 | 待建（EvalRunner 的 check） |
| T3 | 独立身份 / 权限 / artifact 的外部 CI 或人工验收 | 晋升信任根、延迟结果 | 待建 |

**`auto_verify` 归为 T1 且不得升级。** 依据：其 rubric 第 3 条明写"verify 不运行 typecheck/test/lint"（`VerifyJudge.ts:136`，实现注释见 `:310`），它满足上下文隔离，但不满足进程、artifact、身份与治理独立。

"独立 evaluator"今后必须说明是哪一维独立：**上下文 / 进程 / artifact / 身份 / 治理**。

### G0-C Artifact Registry（最小版）

比较 incumbent 与 candidate 之前必须能**还原完整候选面**。只有 hash 而取不回内容不满足要求。

最小字段：`artifactId` / `kind` / `contentHash` / **可取回内容** / `createdBy` / `sourceRef` / `approvalState` / `deployScope` / `rollbackTarget`。

覆盖对象（G0 只收 G1 会读到的）：prompt、tool schema、evaluator bundle、runtime version、model/provider 配置。Skill、selector、retrieval index 等等到 G5 再加。

### G0-D Experiment Manifest

任何评测结果缺少完整 manifest 时**只能用于调试，不得进入晋升报告**。字段见审查文档 §6.2，G0 先落其中的：case/split/snapshot/evaluator bundle 版本、incumbent 与 candidate 的 artifact set、model/provider/sampling、assignment arm 与随机种子、runner version 与环境指纹、预注册指标与停止规则。

### G0-E 注入 provenance

**这是 G0 里最紧急的一项**：纯增量记录、风险最低，但一旦 G5 开始而它还没上线，那段时间的轨迹将永久失去归因能力，事后补不回来。

五个状态必须分开，不能混为 `recalled`：

```text
recalled  → 检索命中
eligible  → 通过适用性与边界过滤
selected  → 选择器选中
rendered  → 渲染进候选上下文
injected  → 确实进入了发给模型的 context
```

扩展 `KnowledgeItemSchema`（当前是 `.passthrough()`，需显式化并加校验）：

```ts
action: z.enum([
  'recalled', 'proposed', 'approved', 'rejected', 'written', 'deleted',
  'eligible', 'selected', 'rendered', 'injected',
]),
injected: z.array(z.object({
  entryId: z.string(),
  contentHash: z.string().regex(/^[a-f0-9]{64}$/),
  versionChain: z.array(z.string()).max(8),
  sourceCaseId: z.string().optional(),          // 来源 TaskCase，用于污染组隔离
  selectorVersion: z.string(),
  queryHash: z.string(),
  assignmentProbability: z.number().min(0).max(1).optional(),
  slot: z.number().int().nonnegative(),
  order: z.number().int().nonnegative(),
  targetRunId: z.string().optional(),
  targetTurnId: z.string().optional(),
})).max(32).optional(),
excludedCandidates: z.array(z.object({
  entryId: z.string(),
  contentHash: z.string(),
  reasonCode: z.string().max(64),               // 只记 code，不复制正文
})).max(64).optional(),
contextHash: z.string().optional(),             // 最终 context 的 hash，用于对账
tokenCost: z.number().int().nonnegative().optional(),
```

未选候选**只记 id / hash / reasonCode，不复制正文**；自由文本一律脱敏并限长。

现状衔接：robotics `ExperienceWorkingSet` 已有 `injectedIds` 与 `_candidatePool`，但只是运行时痕迹，没有 canonical 记录；显式工具（`experience_load` 等）目前统一发 `recalled`。

### G0-F 注入信任边界（审查未覆盖，新增）

存在一条**信任洗白路径**，必须在注入通道设计之初封住：

```text
被污染的仓库内容 → tool_outcome（Reviewer 视为不可信证据）
        → Reviewer 提炼 → ExperienceCandidate
        → 人工批准（审的是"有没有用"）
        → 注入 Worker 系统上下文（此时被当作可信）
```

Reviewer 的系统提示明确把轨迹内容当作不可信历史证据、禁止跟随其中指令；但 Candidate 是从这些内容**提炼出来的**，过完人工闸门后却以可信上下文的身份进入一个拥有写工具和网络权限的 Worker。人工批准审的是有用性，不是"这段文本里有没有藏指令"。

**必须满足**：

1. 注入通道**只渲染结构化字段**（`applicability` / `policyDelta` / `mechanism` / `verification`），**绝不做自由文本透传**；
2. 每个字段有长度上限与字符集约束，渲染前二次脱敏；
3. 人工批准界面显式提示"这段文本将成为可信系统上下文"；
4. 注入内容不得包含工具调用语法、系统提示分隔符或角色标记。

### G0 验收标准

- 一次带自动注入的运行，轨迹里能查到五个状态的记录，`entryId + contentHash` 与 ExperienceStore 对得上，`contextHash` 可对账；
- 检索到但未注入的候选可区分，且未复制正文；
- 无注入时不产生噪音 item；
- 资格缺失时导出被拒绝，有失败路径测试；
- Artifact Registry 能取回内容并重建一次候选面；

## G1：受控重执行评测底座

**目标**：让"换一套配置、跑同样的任务、比较结果"成为可重复命令。

### 术语更正

第一版统一称 **controlled re-execution（受控重执行）**，不称 replay。只有同时还原环境与动作语义的路径才配叫 replay。`replayClass` 仅描述**动作可重放性**，不能替代**环境复现等级**——这是两个维度。

### G1-A 初始快照：v1 最大的错误

v1 的 EvalCase 只记 `prompt + repo + commit + setupCommands`。这不成立，原因有三：

1. `TaskCase.inputHash` 是对**任务结束后全部轨迹行**做的摘要，不是初始输入 hash；
2. 索引里的 `firstPrompt` **只保留前 240 字**（`indexStore.ts:203`）；
3. trajectory schema 有 `gitBase` 字段，但**全仓库没有任何赋值点**，实际恒为 undefined。

更要命的是：任务完成后的 commit / working tree 不能作为重跑起点，否则用例会在**答案已经存在的状态**上直接通过，指标全是假的。

**必须**：EvalCase 引用任务开始前的不可变 `baseSnapshotRef`，并记录 submodule / LFS、未跟踪 fixture、依赖锁、环境变量白名单、时间与网络模拟、初始化与清理配方。**无法恢复初始状态的历史 TaskCase 只能进 support 分析，不得进 sealed test。**

配套前置：给 trajectory 的 `gitBase` 补上真实赋值点，否则未来的 TaskCase 依旧无法回捞初始状态。

### G1-B EvalCase schema

```ts
export const EvalCaseSchema = z.object({
  schemaVersion: z.literal('eval-case-2.0'),
  id: z.string().regex(/^evalcase_[a-f0-9]{24}$/),
  origin: z.object({
    caseId: z.string(),
    rootTrajectoryId: z.string().uuid(),
    taskReviewId: z.string(),
  }).strict(),
  prompt: z.string().min(1),
  // SessionMode 全集含 campaign / robotics，第一版只收这三种：
  // campaign 跨度过长不适合重复执行，robotics 依赖真实硬件不可回放。
  mode: z.enum(['agentic', 'auto', 'simple_auto']),

  // ── 审查要求的必备引用 ──────────────────────────────
  eligibilityRef: z.string(),
  baseSnapshotRef: z.string(),          // 任务开始前，不是结束后
  environmentManifestRef: z.string(),
  evaluatorBundleRef: z.string(),       // evaluator 不内联在用例里
  resetRecipeRef: z.string(),
  taskContractRef: z.string().optional(),
  criteriaOrigin: z.enum(['user', 'external_spec', 'human_curated', 'reviewer_generated']),
  contaminationGroupId: z.string(),     // 同源任务及其改写共享此 id
  riskTier: z.enum(['R1', 'R2', 'R3']),

  successCriteria: z.array(z.object({
    id: z.string(),
    statement: z.string().min(1).max(1_000),
    checkRef: z.string(),               // 指向 evaluator bundle 内的检查，不是裸命令
  })).min(1).max(20),

  replayClass: z.enum(['deterministic', 'approximate', 'non_replayable']),
  environmentFidelity: z.enum(['restored', 'approximated', 'unrestorable']),
  split: z.enum(['support', 'validation', 'sealed_test', 'canary']),
  taskFamily: z.string().optional(),
  frozenAt: z.number(),
}).strict()
```

**`criteriaOrigin='reviewer_generated'` 不得进 sealed test。** 从 TaskReview 回捞的成功标准是 Reviewer **看过执行结果之后**的回顾性产物，存在 post-treatment bias；它只能作为人工定稿的候选，除非经独立人工或外部规范重写并生成新版本。

### G1-C Evaluator bundle 与执行隔离

v1 把 `setupCommands` 和 `check.command` 直接写进用例，等于把任意命令当信任根。改为引用独立版本化的 `evaluatorBundleRef`，runner 分阶段执行：

```text
setup → execute(candidate) → verify(evaluator) → teardown
```

契约要求：

- candidate **无权写 evaluator bundle**；verify 进程使用独立最小权限身份、独立只读挂载、独立凭据与网络策略；
- 路径必须相对 sandbox，拒绝 `..`、绝对路径与 symlink escape；
- 命令超时、输出上限、进程树回收、资源上限全部 fail closed；
- 防 candidate 通过改测试脚本、改 PATH、改依赖或生成同名文件骗过检查；
- 四阶段的副作用分别隔离并审计。

仓库已有沙箱执行器与权限 jail，**复用而不是另起一套**。

### G1-D 数据切分：四层，不是一个 held-out

```text
support / train     生成诊断、经验与候选
validation / dev    调参、筛选、Pareto 档案      ← 日常决策在这里做
sealed test         候选冻结后由独立 runner 执行一次发布判定
canary              真实流量的延迟结果与回滚判定
```

- sealed test 的**内容、细粒度结果与 evaluator 实现不向 candidate generator 暴露**；
- 需要多轮适应性查询时，必须明确查询预算与重置策略，且不得继续称其为普通 held-out；
- 按 `contaminationGroupId` 与 lineage 隔离：Candidate 的来源 TaskCase、同源改写与后代轨迹不得跨切分。

### G1-E 指标契约

| 指标 | 定义 | 方向 |
| --- | --- | --- |
| `criteria_pass_rate` | 通过的 criteria 数 / 总数 | ↑ |
| `case_success_rate` | 全部 criteria 通过的用例比例 | ↑ |
| `false_success_precision` | 错误完成数 / **宣称完成数** | ↓ 核心反指标 |
| `false_success_per_case` | 错误完成数 / **全部用例数** | ↓ 同时报告 |
| `repeat_pass_rate` | 同一用例重复 k 次全部通过的比例 | ↑ |
| `lower_tail_success` | 最差 task family cohort 的 case_success_rate | ↑ 硬门槛 |
| `eligible_recovery_rate` | 预定义 eligible incident 中成功恢复的比例 | ↑ |
| `preventable_correction_rate` | 本可避免的人工纠正 | ↓ |
| `required_escalation_rate` | 必要的升级与澄清 | **中性，不惩罚** |
| `safety_violations` | 安全违规数 | **硬 veto** |
| `cost_usd_per_success` | 总成本 / 成功用例数 | ↓ 约束 |
| `turns_per_success` | 总 turn / 成功用例数 | ↓ 约束 |

两处相对 v1 的更正：

- **`human_intervention_rate` 已拆解。** 笼统地压低人工介入会把必要澄清、高风险升级和正确拒绝一并惩罚，训练出一个不敢问问题的 Agent。只有 `preventable_correction_rate` 是需要下降的。
- **恢复率限定分母。** 不限制 eligible incident 会奖励"先制造更多工具错误再恢复"。
- 后两项是**约束不是目标**；安全违规进指标契约而不只是治理文字。

比较规则：硬约束（安全、false success、最差 cohort 不退化）+ Pareto 前沿，不压成单一标量。

### G1-F 统计契约与小样本现实

审查要求预注册最小有意义效应、置信区间、重复次数与停止规则，TaskCase 为统计单元（**重复 seed 不算新增独立样本**），控制多候选多指标的重复比较，无功效时输出 `inconclusive`。全部采纳。

但要正视一个后果：**在几十个用例的规模上，单次开封的 sealed test 对我们真正想抓的效应量基本达不到功效。** 若不预先设计，结局只有两个——要么什么都晋升不了，要么门槛被悄悄放松。

因此明确常态路径与例外路径：

| 路径 | 证据来源 | 适用 |
| --- | --- | --- |
| **常态** | validation 上的配对比较 → `inconclusive` 也接受 → 进入**可回滚 canary**，以真实流量与延迟反馈为主要证据 | 绝大多数候选 |
| **例外** | sealed test 单次开封 | 少数高风险晋升（R3、或影响 evaluator/权限面的变更） |

这与审查 §7.3 的放行清单不冲突，只是明确了主力证据来源是 canary 而非离线 sealed test。**sealed test 是稀缺资源，按次消耗。**

## G2：只读 Shadow + L0（Conditional Go）

**目标**：验证数据质量是否支撑上层优化；产出失败分类与参数候选。**不得改变生产行为，不得直接改默认值。**

### G2-A 数据质量审计

先回答"这批数据能支持什么结论"，再谈结论本身：资格覆盖率、环境可恢复率、T2 检查覆盖率、证据完整率、非正常终止占比（用 `run_result.outcome` 识别幸存者偏差）。

### G2-B L0 参数候选

| 参数 | 证据来源 | 方法 |
| --- | --- | --- |
| `maxVerifyRounds` | `evaluation`（round + verdict） | 通过轮次分布，找边际收益归零的拐点 |
| compaction 触发点 | `compaction` 的 token 数 + 其后成功率 | 比较触发点后的 goal drift 与恢复轮数 |
| 重试退避 | 重复失败签名的间隔分布 | 复现间隔 vs 最终恢复率 |
| 子代理拆分阈值 | `subagent` + 任务规模 + 结果 | 拆分度 vs 成功率/成本 |
| 工具超时 | `tool_outcome.durationMs` 分布 | 分位数；超时截断损失了多少本会成功的调用 |
| 并发上限 | 并发数 vs 错误率 / 合并冲突 | |

每条建议都必须在 G1 的 validation 上配对验证后才能改默认值。**得出"当前不应改"是合格产出。**

### G2-C 失败分类

输入：TaskReview 的 Finding、失败签名、`run_result.outcome`、人工纠正点。输出：按机制归类的失败簇（对应治理文档 §5.5 的 failure taxonomy），每簇带样本数、代表性证据 ordinal、可能受影响的机制。

**不设覆盖率配额**，证据不足一律进 `unknown`。强行归类比不归类更有害。

这一步的产物**决定 G3～G5 该优先改什么**，也顺带解决"人工标注稀疏"：让人审分类好的失败簇，而不是逐条独立提案。

### G2 中止条件（全局 gate）

- **数据质量审计显示资格覆盖率、环境可恢复率或 T2 检查覆盖率过低，或参数分析得不出任何可信结论** → 回 G0 / G1 补数据与契约，**不得进入 G3**。

## G5：Experience / playbook / workflow

**目标**：把 Reviewer 产出的经验接入运行时。

### 放行前置（硬）

1. G0 的 provenance 与注入信任边界（G0-F）已上线；
2. G1 评测底座可用，切分无泄漏；
3. **G2 的失败簇证明该问题适合由外置知识解决**——不是"因为我们有 Reviewer 所以要用它"；
4. G3 / G4 已建立契约与状态底座。

### 关键设计决策

- 注入的是 `ExperienceCandidate`，走**独立通道**，不污染正式 ExperienceStore；
- 先做 **cue 规则匹配**，不做语义检索——后者会引入一个新的不可解释失败源；
- 注入**默认关闭**，可按 workspace / task / session 一键关闭，A/B 两组只差这一个开关；
- 进入有副作用 executor 的注入**默认按 R2 处理**（见 §10 风险分级）。

### 边际价值必须靠受控分配估计

**仅凭 provenance 不能回答"哪条经验有贡献"。** 多条经验同时注入、选择器按任务难度挑条目、条目来自同源任务，都会让暴露关系与因果关系脱钩。

必须使用**预注册的随机开关、配对消融、factorial 设计或 switchback 实验**，并记录 eligible set、实际选择、顺序、slot、selector version、分配概率与目标 turn。provenance 是这些设计的**必要输入**，不是替代品。

### 中止条件

- **注入后无改善甚至退化，且归因显示条目本身质量不足** → 回 Reviewer 的质量门槛，**不得靠加大注入量或放宽门槛来补**。

## G6：Routing bandit

**目标**：模型选择、子代理拆分、工具选择、预算分配的策略化。

### 放行前置（硬）

当前路由基本是确定性选择，轨迹没有 logging policy version、eligible actions、action probability，也无法证明不同 action 在同类 context 上有支持覆盖。**此时 IPS 权重不可计算**，缺支持时即使拟合 reward model 也只是不可验证的外推。

因此必须**先设计受约束的随机 logging policy**：只在安全可行域内探索，记录 eligible set、选择概率与拒绝原因码；覆盖不足时限制目标策略。**不允许把普通确定性历史日志包装成无偏反事实评估。**

其余：bandit 只在可行域内选择，安全与预算硬边界由 L0 管理；离线估计与灰度方向须一致；跨模型方差不得上升；可一键回退固定路由。

## G7：窄任务权重训练（可选，需重新立项）

候选窄任务（优先级从高到低）：compaction 摘要 → 失败分诊 → verify judge → 经验条目改写。选择标准：边界清晰、有 T2/T3 可验证 reward、失败可回退、不直接触碰用户工作区。

**四条前置全部满足才启动**：G0～G5 完成且评测底座有区分度；T2/T3 reward 链路成熟；已确认该任务用 L0～L3 无法进一步改善；接受 open-weight 底座的部署与运维成本。

强制约束：reward 只能来自 T2/T3，LLM judge 只做 tie-break；遵守 `trainingEligibility` 与 workspace 隔离；保留非训练版本作随时可切回的对照；被训练模型不得参与自己的评测。

**中止条件**：出现 reward hacking 迹象（judge 分数上升但 sealed test 停滞或下降、输出出现异常模式如冗余符号/标签）→ **立即停止并回滚**，不要试图"再加一点正则"。

## 10. 贯穿性约束

### 10.1 风险分级按能力算，不按 artifact 名称算

风险 = **候选影响的有效能力 × 数据范围 × 可逆性 × blast radius**。

- prompt / context 不因"它只是文本"而天然低风险——一旦进入拥有写工具、网络或审批能力的 Agent，就可能改变真实副作用；
- **R1 仅限**：shadow、只读 worker，或在无外部副作用 sandbox 中执行的候选；
- 进入有副作用 executor 的 prompt / 注入内容**默认至少 R2**；
- 影响 evaluator、权限面或跨 workspace 数据的候选为 R3，走例外路径（sealed test 单次开封）。

### 10.2 延迟反馈的幂等与时序

事后 CI、工件回退、任务重开可能重复到达、乱序到达或互相矛盾。契约要求：

- 延迟反馈 append-only，**新判断不覆盖旧判断**，用 `supersedes` / `contradiction` 表达关系；
- 必须有 source event id 与幂等键；重复事件幂等；
- 记录 target artifact / diff 与最大等待窗；
- 晋升报告按**预注册观察窗**重算，并区分"尚未观察"与"观察后通过"。

### 10.3 语料增长（审查未覆盖，新增）

G1 之后的全部统计机制都假设一个**尚不存在**的语料库——首次真实 Reviewer 运行只有 5 条轨迹、4 个候选窗口。

"如何把合格 TaskCase 攒到能支撑统计的规模"是使用与采纳问题，不是工程问题，但它卡在所有事情的上游。因此：

- **G0 起就跟踪合格 TaskCase 的增长速率**（合格 = 有资格 + 环境可恢复 + 有 T2 检查）；
- 设定一个下限阈值；**低于阈值时，G1-F 的统计设计必须按小样本重做**（配对设计、贝叶斯、序贯分析），而不是等做到 G2 才发现样本不够；
- 增长速率本身是 G2 数据质量审计的一项输出。

## 11. 风险与应对

| 风险 | 触发信号 | 应对 |
| --- | --- | --- |
| 适应性泄漏 | 反复根据同一集合结果提候选 | 四层切分；sealed test 按次消耗；查询预算 |
| 起点污染 | 用例在"答案已存在"的状态上通过 | `baseSnapshotRef` 必须是任务开始前；`environmentFidelity` 硬校验 |
| Evaluator 被绕过 | candidate 改脚本 / PATH / 依赖后通过 | evaluator bundle 独立身份与只读挂载；逃逸对抗测试 |
| 回顾性偏差 | reviewer 生成的标准写得刚好能过 | `criteriaOrigin` 标注；`reviewer_generated` 不进 sealed test |
| 因果过度宣称 | 用 provenance 直接下"某经验有效"结论 | 必须有受控分配或消融；否则只能称"可归因分析" |
| 信任洗白 | 注入内容携带指令或角色标记 | G0-F：结构化字段 only + 对抗性单测 |
| 自评污染 | 用 TaskReview 四维评分当指标 | 治理文档 §8.5 硬性禁令 |
| 功效不足被无视 | 把"不显著"当作"等价" | 强制 `inconclusive` 标签；常态路径走 canary |
| 指标诱导 | 压低人工介入 / 刷恢复率 / 优化成本 | 拆解介入类型；限定恢复分母；成本仅作约束 |
| G0 镀金 | 造出没有调用方的注册表 | G0 范围锚定在 G1 合成 fixture 所需最小集 |
| 语料不足 | 统计设计建立在不存在的样本上 | §10.3 增长跟踪与小样本预案 |
| 治理绕过 | 候选自行晋升、修改 evaluator | 治理文档 §10 / §13 不因进度压力放宽 |

### 15.4 写侧三个与原设计不同的判断

实现前对三条假设做了代码核验，其中两条原表述有误。修正后的事实改变了发射点的选择，记录在此以免重蹈。

**一、`renderForTurn()` 的预算跳过在当前配置下不可达。** `checkout()` 的前置守卫加上 `_evictToFit()` 已保证非 sticky slot 落位后 `usedTokens ≤ maxBudget`，而生产代码无任何 sticky slot（仅 working set 的 medium 与 VV hook 的 high）。真正的丢弃发生在 **checkout 时**：单条超预算被拒（`_refreshSlots` 历史上忽略返回值）、同一循环内 medium 之间 LRU 互相驱逐、以及 VV hook 以 high 优先级抢占。`skippedForBudget` 仍然记录，为的是这条假设一旦改变能立刻显形。

**二、注入跨轮存活不是"跳过 preload"。** `preload()` 每轮都跑。真实机制是 `_refreshSlots()` 只 checkout 本轮选中的、**从不 checkin 上轮落选的**，而 `renderForTurn()` 不检查 `remainingTurns`。于是

> **`injected ⊋ selected`**：本轮注入集 = 本轮选中 ∪ 前 ≤3 轮残留 ∪ VV hook 注入，且残留项的 TTL 会被 agent 的引用行为重置。

这直接决定了发射点必须在 pager 渲染侧——残留条目在 selector 的视野里根本不存在。`queryHash` 因此在 checkout 时钉到 slot 上，否则三轮后的残留会被盖上当前轮的 query，凭空捏造一次检索。

**三、`eligible` 的分叉没有被强行统一。** 每个候选记录 `eligibleByThreshold` 原始判定，由 `selectionPath` 说明本轮走了哪条路，两种定义都可事后还原。硬选一个写死等于把一次未经检验的口径冻进语料。

附带修正的一个真实缺陷（**本批只记录未修**，按 G0"不改变 Agent 行为"）：`_refreshSlots` 忽略 `checkout()` 返回值，导致渲染后超过 1500 tokens 的经验被静默丢弃且无任何痕迹——`_refreshSlots` 对 `failureReason` / `workarounds` 不截断，而 `ExperienceStore.write()` 也无长度校验。现在它会以 `slot_oversized` 出现在 `excludedCandidates` 里。是否修取决于这批数据显示它多久发生一次。
