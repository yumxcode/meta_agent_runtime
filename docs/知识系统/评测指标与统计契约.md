## 0. 为什么这份文档必须先于代码

指标的定义是决策，不是实现细节。绝大多数评测事故不是算错了，而是**算对了一个不该算的东西**——分母选错、把"不知道"折叠进"失败"、把"不显著"读成"等价"。这些错误产出的数字**看起来完全正常**，且往往在若干个决策之后才暴露。

因此每条指标都必须回答三个问题：分子是什么、分母是什么、**拿不到证据的样本去哪了**。第三个是本文的重点。

## 1. 三态，不是两态

`EvalRunner` 对每条 criterion 输出三种判定，对应三件不同的事：

| 判定 | 含义 |
| --- | --- |
| `pass` | 候选达成了该 criterion |
| `fail` | 候选未达成 |
| `insufficient_evidence` | **无人知晓**——检查超时、bundle 被改、setup 失败 |

> **铁律：`insufficient_evidence` 既不得计为 `fail`，也不得静默从分母中消失。**

计为 fail 会污染 `false_success_precision`——它的分母是"宣称完成数"，把基础设施故障塞进去会让这个核心反指标失去可读性。而静默丢弃会打开一条更隐蔽的漏洞，见 §4。

## 2. 指标定义

以下"可判定运行"（conclusive run）指该 case 的全部 criteria 都得到 `pass` 或 `fail`。

| 指标 | 分子 | 分母 | 方向 |
| --- | --- | --- | --- |
| `criteria_pass_rate` | `pass` 的 criteria 数 | **已判定**的 criteria 数（`pass`+`fail`） | ↑ |
| `criteria_unresolved_rate` | `insufficient_evidence` 的 criteria 数 | 全部 criteria 数 | ↓ 质量信号 |
| `case_success_rate` | 全部 criteria 均 `pass` 的 case 数 | **可判定**的 case 数 | ↑ |
| `case_inconclusive_rate` | 含任一未判定 criterion 的 case 数 | 全部 case 数 | ↓ 见 §4 |
| `false_success_precision` | 错误完成数 | **宣称完成数** | ↓ **核心反指标** |
| `false_success_per_case` | 错误完成数 | 全部 case 数 | ↓ 同时报告 |
| `repeat_pass_rate` | k 次重复全部成功的 case 数 | 有 k 次重复的 case 数 | ↑ |
| `lower_tail_success` | — | 最差 task family 的 `case_success_rate` | ↑ **硬门槛** |
| `cost_usd_per_success` | 总成本 | 成功 case 数 | ↓ **约束非目标** |
| `turns_per_success` | 总 turn 数 | 成功 case 数 | ↓ **约束非目标** |
| `safety_violations` | 安全违规数 | — | **硬 veto** |

### 2.1 "宣称完成"的操作化定义

`false_success_precision` 只有在"宣称"可观测时才有意义。定义为：

> **宣称完成** = 候选自己认为任务已完成（`execute` 阶段退出码为 0）。
>
> **错误完成** = 宣称完成，但该 case 的 criteria 判定为未达成。

这是整套指标里唯一能抓住"Agent 自信地交付了错误结果"的量，因此它是核心反指标。注意它的分母**不是全部 case**——一个从不宣称完成的 Agent 在这个指标上完美，所以必须与 `false_success_per_case` 同时报告，两者缺一都可被玩弄。

未判定的运行两个口径都排除，但计入 `case_inconclusive_rate`。

### 2.2 三个刻意不作为优化目标的量

- `cost_usd_per_success` / `turns_per_success` 是**约束**：越过预算即拒绝，但压低它们不构成改进。把成本当目标会训练出一个偷工减料的 Agent。
- `required_escalation_rate`（必要的升级与澄清）**中性，不惩罚**。压低笼统的"人工介入率"会把必要澄清、高风险升级和正确拒绝一并惩罚，训练出一个不敢问问题的 Agent。只有 `preventable_correction_rate`（本可避免的纠正）需要下降。
- `eligible_recovery_rate` 的分母**必须**限定为预定义的 eligible incident。不限定会奖励"先制造更多工具错误再恢复"。

> 这两项（`preventable_correction_rate`、`eligible_recovery_rate`）依赖尚不存在的人工标注与 incident 定义，当前**不计算**，在报告中列为未测量而非填零。

## 3. 统计契约

### 3.1 统计单元是 TaskCase

**重复 seed 不产生新的独立样本。** 同一 case 跑 5 遍是 1 个样本的 5 次观测，用于估计 `repeat_pass_rate` 与方差，不得当作 5 个样本喂进检验。

### 3.2 配对比较，不是两个独立比例

incumbent 与 candidate 跑**同一批 case**，因此比较必须配对。每个 case 落入四格之一：

```
            candidate 成功   candidate 失败
incumbent 成功      a              b
incumbent 失败      c              d
```

`a` 与 `d` 不携带差异信息；证据全部来自**不一致对** `b` 与 `c`。小样本下用 McNemar 精确检验（对 `b+c` 次试验、`p=0.5` 的二项分布做双侧精确检验），不用卡方近似——几十个用例的规模上近似不成立。

### 3.3 「不显著」不是「等价」

> **`equivalent` 只能由等价检验产出，不得由"p 值不显著"产出。**

这是本契约最重要的一条。判定规则：

| 条件 | 判定 |
| --- | --- |
| 精确检验 p < α 且方向为候选更优 | `candidate_better` |
| 精确检验 p < α 且方向为现任更优 | `incumbent_better` |
| 差异的置信区间**完全落在** ±MDE 之内 | `equivalent` |
| 其余一切情况 | `inconclusive` |

最后一行是常态而非例外。在几十个用例的规模上，单次开封的 sealed test 对我们真正想抓的效应量基本达不到功效——预期结论就是 `inconclusive`，这是**合格产出**，不是失败。

若不预先接受这一点，结局只有两个：要么什么都晋升不了，要么门槛被悄悄放松。因此主力证据路径是**可回滚 canary 的真实流量与延迟反馈**，sealed test 是稀缺资源、按次消耗。

### 3.4 多重比较

同时评估多个候选或多个指标时，必须声明控制方式（`bonferroni` / `benjamini_hochberg` / `preregistered_single`）。未声明即视为未控制，其结果不得进入晋升报告。

### 3.5 预注册

`PreRegistration`（见 `src/evolution/ExperimentManifest.ts`）必须在跑之前冻结，且 `minimumDetectableEffect` 为必填——没有它，"无显著差异"会被读成"等价"，这是欠功效比较放行坏决策最常见的路径。

## 4. 差异性不可判定：一条必须堵死的漏洞

把未判定运行排除出 `case_success_rate` 的分母是正确的（否则一次 runner 故障看起来像质量退化），但这**打开了一条攻击面**：

> 一个让更多运行变得不可判定的候选——例如引发超时、让检查崩溃——会因为这些运行被丢弃而**显得更好**。

因此：

> **守卫：比较两臂的 `case_inconclusive_rate`。若差异超过预注册阈值，整个比较判为 `inconclusive` 并附明确原因，不得输出效应量。**

这条守卫的存在本身比它拦住的具体数字更重要——它把"丢弃不可判定样本"从一个隐式假设变成一个被检验的前提。

## 5. 报告要求

任何比较报告必须同时给出：

1. 两种 `false_success` 口径；
2. `case_inconclusive_rate`（分臂）与差异性守卫的结论；
3. 效应量 + 置信区间 + 精确检验 p 值 + 不一致对计数 `b` / `c`；
4. 判定（四选一）及其依据；
5. 明确列出**未测量**的维度，而非填零。

缺少任何一项的结果只能用于调试，不得进入晋升报告。
