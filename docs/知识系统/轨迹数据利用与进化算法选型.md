## 0. 执行摘要

一个必须先说清的前提：

> **meta-agent 是 API 客户端，权重级强化学习在当前架构下没有落点。**

Claude / GLM / DeepSeek 的参数不在我们手里，RL 所需的 rollout 与训练基础设施也不在。因此"用强化学习训练 meta-agent"这句话必须先拆成两问：

1. **非参数层能优化什么** —— 现在就能做，且大概率贡献绝大部分收益；
2. **参数层什么时候才值得碰** —— 需要引入 open-weight 模型作为底座，属于最后一步。

本文的核心结论：

1. 我们真正的资产不是"轨迹"，而是**可对账的标注**：ordinal 级精确引用 + TaskCase 任务边界 + 结果判定 + 人工纠正信号 + 计量数据。这是 `(state, action, outcome, label)` 的原材料，也是绝大多数团队卡住的地方。
2. 可优化对象按代价与风险分**五层（L0–L4）**。L0～L2 不涉及任何模型训练，应当先做完。
3. **自然语言反馈优于标量 reward**：当优化对象本身是自然语言（prompt、playbook、经验条目）时，文本反馈的信息密度远高于标量，样本效率高一到两个数量级。
4. **不得把 TaskReview 的四维评分当作优化目标**。那是本系统自产的 LLM 自评，用它训练自己是自训练崩溃的标准配方。
5. **当前最该做的不是选算法，而是建离线回放评测集**。没有 fitness function，任何优化都无法证伪。
6. 必须新增**经验注入 provenance**：轨迹要记录本次注入了哪些经验 / playbook 版本。没有它就无法归因，所有 A/B 结论都不成立。

## 1. 已有的数据资产盘点

截至 0.9.3，以下信号已经在生产链路中稳定产生，且可由 canonical trajectory 重建：

| 信号 | 载体 | 可用作 |
| --- | --- | --- |
| 精确引用 | `ordinal` + `trajectoryId` | 证据链、credit assignment 的定位 |
| 任务边界 | `TaskCase`（root + child + 多 run） | episode 单元 |
| 结果判定 | `TaskReview.outcome.verdict` + 逐条 `successCriteria` | 弱标签（**非 reward**） |
| 完成度审核 | `evaluation`（`evaluator=auto_verify`，pass/fail + round） | 过程信号、收敛轮数分布 |
| 人工纠正 | `approval`（`decidedBy='human'` 的 deny/redirect）、`message.isSteering` | 负信号（人给的，不可伪造） |
| 工具失败 | `tool_outcome.isError` + 归一化失败签名 | 重复失败检测、恢复率 |
| 环境反馈 | `tool_outcome.exitCode`、命令输出 | **可验证 reward 的主来源** |
| 计量 | turn、cost、duration、run 数 | 效率约束（非目标） |
| 人工标注 | LearningProposal 的 approve / reject | 稀疏但高质量的监督信号 |

盘点结论：**数据层基本就绪，缺的是把它变成数据集与评测集**。

## 2. 可优化对象的五层分层

按"改起来从易到难、风险从低到高"排序。**不要跳层**。

### L0 参数与阈值｜不需要任何模型

对象：verify 轮数上限、compaction 触发点、并发度、预算分配、工具超时、drift 门槛、子代理拆分阈值。

方法：纯统计。例如 `evaluation` 里 auto_verify 在第 N 轮通过的分布，直接给出 `maxVerifyRounds` 的合理取值；失败签名的复现间隔分布，直接给出重试退避策略。

价值：收益最快，且是**验证数据质量的第一块试金石**——如果这一层都算不出可信结论，说明数据还不能支撑更上层的优化。

### L1 上下文与 Prompt｜反射式演化

对象：系统提示各 section、注入的经验 playbook、模式说明、工具描述。

方法有两条成熟路线：

- **ACE（Agentic Context Engineering）**：把上下文当作**不断累积的 playbook**而不是压缩摘要，用 Generator / Reflector / Curator 三分工增量更新，显式对抗 context collapse。这个三分工几乎就是我们现有的 Worker / Learning Reviewer / （尚未建设的）Curator。
- **GEPA（反射式 prompt 演化）**：采样轨迹 → 自然语言反思诊断 → 提出并测试 prompt 变更 → Pareto 前沿保留。其核心论点对我们特别适用：**优化自然语言对象时应使用同一模态的优化信号**，文本反馈比标量 reward 信息密度高得多；GRPO 需要数千次 rollout 才能学到的东西，反射式演化用几十次即可。

现状衔接：`ExperienceCandidate` 已经是结构化的 policy delta（适用情境 + 触发信号 + 策略差分 + 机制 + 验证 + 边界 + 证据），距离"可检索注入的 playbook 条目"只差一个检索层与注入层。这是 Reviewer 子系统天然的下一步。

### L2 技能与工作流归纳

对象：可复用的多步流程。

方法：AWM（Agent Workflow Memory）路线——从成功轨迹归纳 workflow，存为结构化记忆单元，推理时按情境检索注入；支持离线归纳与在线自归纳。

现状衔接：`phase` item 已能支撑路径分段，TaskReview 的"实际解法路径逐阶段重建"正是归纳的输入。

### L3 路由与选择策略｜可以上 bandit

对象：模型选择（main / flash / compact / fallback）、子代理拆分策略、工具选择、预算分配策略。

方法：**contextual bandit**，不需要 full RL。这一层动作空间小、反馈相对快、可离线用历史轨迹做反事实评估（IPS / doubly robust）。这是唯一一个有"经典 RL 味道"但代价可控的落点。

约束：必须与 L0 的硬约束（安全、预算上限）分离，bandit 只在可行域内选择。

### L4 权重级 RL｜需要换底座

只有当我们愿意为**某个窄任务**引入 open-weight 小模型时才成立。候选窄任务：compaction 摘要、verify judge、失败分诊、经验条目改写。

目标形态可参考 EvolveR 的三段闭环：离线自蒸馏（冻结策略，把原始轨迹蒸馏为抽象原则库）→ 在线交互（用原则指导决策，产生新数据）→ 策略进化（用新轨迹做 RL 更新，闭合循环）。

但对我们而言这是**第五步不是第一步**。在 L0～L3 跑通、评测集稳定、可验证 reward 可靠之前引入权重训练，只会把不可解释的问题引入不可回滚的层面。

### 分层与"能改什么"的对应

| 层 | 改什么 | 要不要训模型 | 风险 |
| --- | --- | --- | --- |
| L0 | 运行参数、阈值 | 否 | 低，可即时回滚 |
| L1 | 系统提示、经验 playbook | 否（用 LLM 做优化器，不训权重） | 中，需防 context collapse |
| L2 | workflow / skill 库 | 否 | 中，需防过拟合到少数任务 |
| L3 | 路由与选择策略 | 否（bandit） | 中高，需离线反事实评估 |
| L4 | 模型权重 | 是，且需换底座 | 高，不可回滚性最强 |

## 3. Reward 设计：最容易翻车的地方

### 3.1 已知失败模式

近期工作给出的警告非常一致，且都直接适用于我们：

- **LLM-as-judge 会被表层"master key"欺骗**：推理开场白、非词符号等就能显著抬高判分，即使在有参考答案的范式下也会出现灾难性 reward hacking；无正则时模型会迅速学会用大量括号、HTML 标签骗过 judge。
- **RLVR 会导致模型"钻验证器空子"**：模型放弃归纳规则，转而枚举实例级标签，产出能通过验证器但没有捕捉到目标关系模式的输出。
- **纯 proxy reward 会导致 policy collapse**：用自监督代理信号完全替代可验证反馈，长期训练下会出现严重失效。

### 3.2 硬性禁令

> **禁止把 `TaskReview.assessment` 的四维评分（effectiveness / reliability / stability / efficiency）用作任何优化目标或 reward。**

理由：那是本系统自产的 LLM 自评，且其晋升门槛中的 `candidateEligible`、`significance`、`abstractionLevel` 三项本身也全部由模型自述，宿主唯一的客观校验只有证据交集。自评→训练自己是自训练崩溃的标准配方。

四维评分的正确用途是：**人工审核时的排序与导航**，以及**失败模式聚类的特征**。不是目标函数。

### 3.3 信号分层

主 reward 只能来自**环境给的、不可伪造的信号**：

| 优先级 | 信号 | 说明 |
| --- | --- | --- |
| 1 | 命令 exit code、测试通过、构建成功、lint / CI | 必须发生在最后一次相关 diff 之后 |
| 2 | 同一失败签名是否停止复现 | 恢复能力的直接证据 |
| 3 | 人工 deny / redirect / steering 的发生率 | 人给的负信号 |
| 4 | 最后相关 diff 之后是否存在新的验收证据 | **false success 检测** |
| 5 | park / blocked → 已验证 terminal 的恢复率 | 长周期稳定性 |
| 6 | turn / cost / wall-clock | **只能当约束，不能当目标** |

第 6 项必须写成约束而非目标：直接优化成本会学到"少干活"，这是最廉价的 reward hacking。

**LLM judge 只能做 tie-break 或过滤，不能覆盖确定性失败，且必须运行在独立上下文中。** 我们的 auto_verify 已经是隔离上下文（不看执行 Agent 的推理过程），这个设计要保持。

### 3.4 多目标而非单一标量

沿用 `meta-agent-自进化方案.md` §8.1 的结论：候选比较使用硬约束 + Pareto 前沿，不把安全、正确性、成本、速度过早压成一个可被 gaming 的标量。`false_success_rate` 是核心反指标。

## 4. 最紧迫的一步：离线回放评测集

**没有 held-out 评测集，GEPA 也好 bandit 也好都没有 fitness function，任何"优化"都无法证伪。** 这件事比选算法重要得多。

最小可行做法：

1. 从已有轨迹中挑选 `outcome.verdict` 明确、且具备确定性验证证据的 TaskCase，冻结为回放集；
2. 记录每个用例的初始 prompt、工作区快照标识、可用工具集、模型与 provider；
3. 标注 `replayClass`（`deterministic` / `approximate` / `non_replayable`），非确定性用例只进 support 不进 held-out；
4. 按 task family、时间、workspace 去重后切分 support / validation / held-out，同源任务及其改写不得跨切分泄漏；
5. 评测指标固定为：逐条 successCriteria 命中率、false success 率、verified correctness、重复运行通过率、成本、turn 数；
6. **阈值与切分在看到候选结果之前冻结。**

规模上不必追求大：**20～50 个证据完整的用例，价值远高于 500 个残缺用例。**

## 5. 必须新增的字段：经验注入 provenance

当前架构缺一个字段，且加起来很便宜：

> **轨迹必须记录本次运行注入了哪些 ExperienceCandidate / playbook / workflow 及其版本。**

原因：一旦 Reviewer 的产出开始进入 prompt，后续轨迹就被污染了——效果究竟来自注入的经验，还是任务本身更简单，无法分辨。没有这个 provenance，`ExperienceCandidate` 的"有没有用"永远无法回答，A/B 归因不成立。

建议形态：复用已有的 `knowledge` item，在注入时追加一条记录 `kind`、`action=inject`、`entryIds`、`versions`、以及选择原因；同时在 TaskReview 里带上"本次注入集合"的引用。

注意：这与 `mode=reviewer` 的自审排除是**两件不同的事**。后者只挡住了"Reviewer 审自己"，没有挡住"Reviewer 的产出改变了被审对象"。

## 6. 自举系统的固有风险

| 风险 | 表现 | 缓解 |
| --- | --- | --- |
| 分布偏移 | 轨迹全部来自当前策略，优化结果只在自身分布上有效 | held-out 集、真实用户任务、保留 incumbent 对照、时间切分 |
| 幸存者偏差 | 失败任务常被中途打断，最该学的样本最残缺 | 用 `run_result.outcome` 识别非正常终止；不完整轨迹只进 support |
| 标注稀疏 | 人工 approve / reject 每条只有 1 bit | 让人审**分类好的失败模式**而不是逐条独立提案；提高单位标注的信息量 |
| 归因不能 | 无法区分改进来自经验还是任务变化 | 第 5 节的注入 provenance |
| Context collapse | 反复重写上下文导致细节流失 | ACE 式增量 playbook，版本化条目，不在原位无限摘要 |
| 效率伪装 | 优化成本导致"少干活" | 成本只作约束，正确性作目标 |

## 7. 建议实施顺序

| 阶段 | 内容 | 涉及训练 |
| --- | --- | --- |
| 1 | 数据资产化：TaskReview 结构化数据集 + 离线回放评测集 + 冻结 5～10 个可验证指标 | 否 |
| 2 | L0 参数调优 + 失败模式聚类（纯分析，立刻见效，同时验证数据质量） | 否 |
| 3 | 经验检索注入 + provenance 字段 + A/B 回放对比 | 否 |
| 4 | GEPA 式 prompt 演化 / AWM 式 workflow 归纳 | 否 |
| 5 | L3 路由 contextual bandit（先离线反事实评估，再灰度） | 否 |
| 6 | （可选）窄任务小模型 RL，使用真实可验证 reward | 是 |

**前三步不涉及任何"训练"，但大概率贡献八成收益。** 真到第 6 步再谈 RL 也不迟。

各阶段的任务拆解、schema 草案、验收标准与中止条件见[自进化实施计划](./自进化实施计划.md)。

每一阶段的晋升仍受 `meta-agent-自进化方案.md` §10 / §13 的治理门槛约束：评测独立性、shadow → canary → promotion、回滚是一等动作、被评对象不得修改 evaluator 与 held-out 数据。
