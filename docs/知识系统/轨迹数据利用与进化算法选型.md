## 0. 执行摘要

一个必须先说清的前提：

> **meta-agent 是 API 客户端，权重级强化学习在当前架构下没有落点。**

Claude / GLM / DeepSeek 的参数不在我们手里，RL 所需的 rollout 与训练基础设施也不在。因此"用强化学习训练 meta-agent"必须先拆成两问：

1. **非参数层能优化什么** —— 现在就能做，且大概率贡献绝大部分收益；
2. **参数层什么时候才值得碰** —— 需要引入 open-weight 模型作为底座，属于最后一步。

核心结论：

1. 我们的资产是**可对账的审计记录**：ordinal 级精确引用 + TaskCase 证据边界 + 结果判定 + 人工纠正信号 + 计量数据。**审计与弱标注读取底座已就绪；可重复评测、数据资格与实验归因尚未就绪**（见 §1）。
2. 可优化对象按代价与风险分**五层（L0–L4）**。L0～L2 不涉及任何模型训练，应先做完。
3. **自然语言反馈优于标量 reward**：当优化对象本身是自然语言时，文本反馈的信息密度远高于标量，样本效率高一到两个数量级。
4. **不得把 TaskReview 的四维评分当作优化目标**。那是本系统自产的 LLM 自评（T1 级），用它训练自己是自训练崩溃的标准配方。
5. **当前最该做的不是选算法，而是建信任与测量底座**：数据资格、evaluator 分级、artifact registry、experiment manifest、注入 provenance、受控重执行评测集。没有 fitness function，任何优化都无法证伪。
6. **provenance 是归因的必要条件，不是充分条件**。因果结论还需要受控分配或消融（见 §5）。

## 1. 数据资产盘点：就绪与未就绪

截至 0.9.3，以下信号已在生产链路稳定产生，且可由 canonical trajectory 重建：

| 信号 | 载体 | 可用作 | Evaluator 等级 |
| --- | --- | --- | --- |
| 精确引用 | `ordinal` + `trajectoryId` | 证据链定位 | — |
| 任务边界 | `TaskCase`（root + child + 多 run） | **证据边界与评测单元** | — |
| 结果判定 | `TaskReview.outcome.verdict` + 逐条 `successCriteria` | 弱标签（**非 reward**） | T1 |
| 完成度审核 | `evaluation`（`evaluator=auto_verify`） | 过程弱信号、收敛轮数分布 | **T1** |
| 人工纠正 | `approval`（`decidedBy='human'`）、`message.isSteering` | 负信号（人给的，不可伪造） | T3 |
| 工具失败 | `tool_outcome.isError` + 归一化失败签名 | 重复失败检测、恢复率 | T2 |
| 环境反馈 | `tool_outcome.exitCode`、命令输出 | **可验证 reward 的主来源** | T2 |
| 计量 | turn、cost、duration、run 数 | 效率约束（非目标） | — |
| 人工标注 | LearningProposal 的 approve / reject | 稀疏但高质量的监督信号 | T3 |

### 术语更正：TaskCase 是证据边界，不是因果单元

TaskCase 把 root + child + 多 run 聚成稳定的证据范围，这使它成为很好的**评测单元**。但它没有 treatment assignment、没有对照组、没有反事实，**不能称为因果单元**。v1 的这个说法已更正。

### 未就绪的部分

盘点结论不是"数据层基本就绪"，而是：

> **审计与弱标注读取底座就绪；可重复评测、数据资格和实验归因未就绪。**

具体缺口（详见治理文档 §6.2 与实施计划 G0/G1）：

- **数据资格**：`trainingEligibility` / workspace 授权尚不存在，真实轨迹目前没有进入评测集的合法通道；
- **初始状态**：`TaskCase.inputHash` 是任务**结束后**全部轨迹行的摘要；`firstPrompt` 只留前 240 字；`gitBase` 字段存在但**全仓库无赋值点**——当前无法恢复"任务开始前"的可执行环境；
- **evaluator 独立性**：`auto_verify` 是 T1（其 rubric 明写不运行 typecheck/test/lint），尚无 T2 确定性检查通道；
- **候选面还原**：无 artifact registry 与 experiment manifest，无法复现候选比较；
- **注入痕迹**：只有运行时 `injectedIds`，无 canonical provenance。

## 2. 可优化对象的五层分层

按"改起来从易到难、风险从低到高"排序。**不要跳层。**

### L0 参数与阈值｜不需要任何模型

对象：verify 轮数上限、compaction 触发点、并发度、预算分配、工具超时、drift 门槛、子代理拆分阈值。

方法：纯统计。例如 `evaluation` 里 auto_verify 在第 N 轮通过的分布，直接给出 `maxVerifyRounds` 的合理取值。

价值：收益最快，且是**验证数据质量的第一块试金石**——这一层都算不出可信结论，说明数据还不能支撑更上层的优化。

### L1 上下文与 Prompt｜反射式演化

对象：系统提示各 section、注入的经验 playbook、模式说明、工具描述。

两条成熟路线：

- **ACE**：把上下文当作**不断累积的 playbook**而非压缩摘要，用 Generator / Reflector / Curator 三分工增量更新，显式对抗 context collapse。这三分工几乎就是我们的 Worker / Learning Reviewer / （尚未建设的）Curator。
- **GEPA**：采样轨迹 → 自然语言反思诊断 → 提出并测试 prompt 变更 → Pareto 前沿保留。核心论点对我们特别适用：**优化自然语言对象时应使用同一模态的优化信号**。

**外推边界**：GEPA 在六类任务上报告比 GRPO 更少 rollout、更高平均结果，说明这个方向值得试验；**不能外推为所有 runtime 机制都能以相同样本效率提升**。ACE 支持增量 playbook 与 context-collapse 风险的判断，但其 benchmark 不能证明我们的月级 park/wake、模型切换与 workspace 漂移问题已解决。

### L2 技能与工作流归纳

对象：可复用的多步流程。方法：AWM 路线——从成功轨迹归纳 workflow，存为结构化记忆单元，按情境检索注入。`phase` item 与 TaskReview 的路径重建是输入。

### L3 路由与选择策略｜bandit，但有硬前置

对象：模型选择（main / flash / compact / fallback）、子代理拆分、工具选择、预算分配。

方法：**contextual bandit**，不需要 full RL。动作空间小、反馈快。

**但离线反事实评估有硬前置**：IPS / doubly robust 需要 logging policy version、eligible actions、action probability 与支持覆盖。当前路由基本是确定性选择，轨迹**不具备这些前提**——此时 IPS 权重不可计算，缺支持时即使拟合 reward model 也只是不可验证的外推。

因此必须**先设计受约束的随机 logging policy**（只在安全可行域内探索，记录 eligible set、选择概率与拒绝原因码），再谈 OPE 与灰度。**不允许把普通确定性历史日志包装成无偏反事实评估。**

### L4 权重级 RL｜需要换底座

只有当我们愿意为**某个窄任务**引入 open-weight 小模型时才成立。候选：compaction 摘要、失败分诊、verify judge、经验条目改写。

目标形态可参考 EvolveR 的三段闭环：离线自蒸馏 → 在线交互 → 策略进化。但这是**最后一步**：在 L0～L3 跑通、评测底座稳定、T2/T3 reward 可靠之前引入权重训练，只会把不可解释的问题引入不可回滚的层面。

### 分层对照

| 层 | 改什么 | 要不要训模型 | 风险 |
| --- | --- | --- | --- |
| L0 | 运行参数、阈值 | 否 | 低，可即时回滚 |
| L1 | 系统提示、经验 playbook | 否（用 LLM 做优化器，不训权重） | **进入有副作用 executor 时至少 R2** |
| L2 | workflow / skill 库 | 否 | 中，需防过拟合到少数任务 |
| L3 | 路由与选择策略 | 否（bandit） | 中高，需随机 logging policy 前置 |
| L4 | 模型权重 | 是，且需换底座 | 高，不可回滚性最强 |

**风险不按 artifact 名称判断。** prompt / context 不因"只是文本"而天然低风险——一旦进入拥有写工具、网络或审批能力的 Agent，就可能改变真实副作用。风险 = 影响的有效能力 × 数据范围 × 可逆性 × blast radius。

## 3. Reward 设计：最容易翻车的地方

### 3.1 已知失败模式

- **LLM-as-judge 会被表层"master key"欺骗**：推理开场白、非词符号即可显著抬高判分；无正则时模型会迅速学会用冗余括号、HTML 标签骗过 judge。
- **RLVR 会导致模型钻验证器空子**：放弃归纳规则，转而枚举实例级标签，产出能通过验证器但没捕捉到目标关系模式的输出。
- **纯 proxy reward 会导致 policy collapse**：用自监督代理信号完全替代可验证反馈，长期训练下出现严重失效。

### 3.2 硬性禁令

> **禁止把 `TaskReview.assessment` 的四维评分用作任何优化目标、reward 或晋升阈值。**

两条理由：

1. 它是**本系统自产的 T1 级 LLM 自评**。用自己的评分训练自己是自训练崩溃的标准配方。
2. TaskReview 的经验晋升门槛中，`candidateEligible`、`significance`、`abstractionLevel` **全部由模型自述**，宿主唯一的客观校验只有"提案证据与 Finding 证据存在交集"。这些字段能守住人工审核队列的信噪比，不具备作为目标函数的抗 gaming 能力。

正确用途：**人工审核时的排序与导航**，以及**失败模式聚类的特征**。

同理，`LearningProposal` 的 `impact` 三档也是模型自述，不得进入多目标向量。

### 3.3 Evaluator 信任分级

"独立 evaluator"必须说明是哪一维独立：**上下文 / 进程 / artifact / 身份 / 治理**。

| 等级 | 含义 | 可用作 | 当前实例 |
| --- | --- | --- | --- |
| T0 | executor 自报 | 仅展示 | 最终助手消息、`run_result` |
| T1 | 隔离上下文 LLM judge | critique、过程弱信号、人工导航 | **`auto_verify`** |
| T2 | 独立进程的确定性检查 | 主要自动指标 | 待建 |
| T3 | 独立身份 / 权限 / artifact 的外部 CI 或人工验收 | 晋升信任根、延迟结果 | 待建 |

`auto_verify` 只满足上下文隔离（其 rubric 第 3 条明写不运行 typecheck/test/lint），**不得因为 item 类型叫 `evaluation` 就升级为 reward**。

### 3.4 信号来源

主 reward 只能来自 **T2 / T3** 的、环境给的、不可伪造的信号：

| 优先级 | 信号 | 等级 | 说明 |
| --- | --- | --- | --- |
| 1 | 命令 exit code、测试通过、构建成功、lint / CI | T2/T3 | 必须发生在最后一次相关 diff 之后 |
| 2 | 同一失败签名是否停止复现 | T2 | 恢复能力的直接证据 |
| 3 | 人工 deny / redirect / steering | T3 | 人给的负信号 |
| 4 | 最后相关 diff 之后是否存在新的验收证据 | T2 | **false success 检测** |
| 5 | park / blocked → 已验证 terminal 的恢复率 | T2 | 长周期稳定性 |
| 6 | turn / cost / wall-clock | — | **只能当约束，不能当目标** |

第 6 项必须写成约束：直接优化成本会学到"少干活"，是最廉价的 reward hacking。

**T1 judge 只做 tie-break 或过滤，不能覆盖确定性失败。**

### 3.5 指标方向不能想当然

几个会诱导错误行为的写法（已在实施计划的指标契约中更正）：

- `human_intervention_rate ↓` 会把必要澄清、高风险升级和正确拒绝一并惩罚，训练出不敢问问题的 Agent。必须拆成 preventable correction（↓）、required escalation（中性）、user clarification、safety denial。
- `recovery_rate` 不限制分母会奖励"先制造更多工具错误再恢复"。只统计预定义的 eligible incident。
- `false_success_rate` 必须说明分母：同时报告 precision 口径（/ 宣称完成数）与 per-case 口径（/ 全部用例数）。
- 安全违规是**硬 veto**，必须进指标契约，不能只存在于治理文字。

### 3.6 多目标而非单一标量

候选比较使用硬约束 + Pareto 前沿，不把安全、正确性、成本、速度过早压成一个可被 gaming 的标量。`false_success` 是核心反指标。

## 4. 测量底座：受控重执行，不是 replay

**没有测量底座，GEPA 也好 bandit 也好都没有 fitness function。** 这比选算法重要得多。

### 4.1 称谓更正

第一版统一称 **controlled re-execution（受控重执行）**。只有同时还原环境与动作语义的路径才配叫 replay。`replayClass` 仅描述**动作可重放性**，不能替代**环境复现等级**（`environmentFidelity`）——这是两个维度。

### 4.2 起点必须是任务开始前

任务完成后的 commit / working tree **不能**作为重跑起点，否则用例会在答案已存在的状态上直接通过。EvalCase 必须引用不可变的 `baseSnapshotRef`，并记录 submodule / LFS、未跟踪 fixture、依赖锁、环境变量白名单、时间与网络模拟、初始化与清理配方。

无法恢复初始状态的历史 TaskCase **只能进 support 分析，不得进 sealed test**。

### 4.3 数据切分：四层，不是一个 held-out

```text
support / train     生成诊断、经验与候选
validation / dev    调参、筛选、Pareto 档案      ← 日常决策在这里
sealed test         候选冻结后由独立 runner 执行一次发布判定
canary              真实流量的延迟结果与回滚判定
```

**反复根据同一集合的结果选择新假设，会对该集合本身过拟合**；"定期换血"不能消除已经发生的适应性泄漏。sealed test 的内容、细粒度结果与 evaluator 实现不向 candidate generator 暴露；需要多轮适应性查询时必须明确查询预算与重置策略，且不得再称其为普通 held-out。

按 lineage 与污染组隔离：候选的来源 TaskCase、同源改写与后代轨迹不得跨切分。

### 4.4 小样本现实

预注册最小有意义效应、置信区间、重复次数与停止规则；TaskCase 是统计单元（**重复 seed 不算新增独立样本**）；无功效时输出 `inconclusive`，不把"不显著"等同于"等价"。

但在几十个用例的规模上，单次开封的 sealed test 对我们想抓的效应量基本达不到功效。因此**常态路径是 validation 配对比较 + 可回滚 canary（以真实流量与延迟反馈为主要证据）**，sealed test 作为稀缺资源留给少数高风险晋升。详见实施计划 §G1-F。

## 5. 注入 provenance：必要而不充分

轨迹必须记录本次运行注入了哪些经验 / playbook / workflow 及其版本。五个状态分开记录：`recalled` / `eligible` / `selected` / `rendered` / `injected`。

### 5.1 为什么必要

一旦 Reviewer 的产出进入 prompt，后续轨迹即被污染——效果来自经验还是任务本身更简单，无法分辨。**这与 `mode=reviewer` 的自审排除是两件事**：后者只挡住"Reviewer 审自己"，没有挡住"Reviewer 的产出改变了被审对象"。

### 5.2 为什么不充分

**仅凭 provenance 不能回答"哪条经验有贡献"。** 记录 `injectedIds` 只能证明**暴露关系**；多条经验同时注入、选择器按任务难度挑条目、条目来自同源任务，都会让暴露与因果脱钩。

因果结论必须来自**预注册的随机开关、配对消融、factorial 设计或 switchback 实验**，并记录 eligible set、实际选择、顺序、slot、selector version、分配概率与目标 turn。

> provenance 支持"可归因分析"，**不单独支持因果宣称**。

### 5.3 注入是信任边界

存在一条信任洗白路径：被污染的仓库内容 → `tool_outcome`（Reviewer 视为不可信证据）→ 提炼为 Candidate → 人工批准（审的是"有没有用"）→ 作为**可信**系统上下文进入拥有写工具的 Worker。

注入通道必须**只渲染结构化字段**，绝不做自由文本透传；字段限长限字符集、渲染前二次脱敏；拒绝工具调用语法、系统提示分隔符与角色标记；人工批准界面显式提示"这段文本将成为可信系统上下文"。详见实施计划 G0-F。

## 6. 自举系统的固有风险

| 风险 | 表现 | 缓解 |
| --- | --- | --- |
| 适应性泄漏 | 反复根据同一集合结果提候选 | 四层切分；sealed test 按次消耗 |
| 起点污染 | 用例在"答案已存在"的状态上通过 | `baseSnapshotRef` 必须是任务开始前 |
| 分布偏移 | 轨迹全来自当前策略，优化只在自身分布有效 | 保留 incumbent 对照；时间切分；`lower_tail_success` 硬门槛 |
| 幸存者偏差 | 失败任务常被中途打断，最该学的样本最残缺 | `run_result.outcome` 识别非正常终止；残缺样本只进 support |
| 回顾性偏差 | Reviewer 事后写的成功标准刚好能过 | `criteriaOrigin` 标注；`reviewer_generated` 不进 sealed test |
| 标注稀疏 | 人工 approve/reject 每条只有 1 bit | 让人审**分类好的失败簇**而非逐条提案 |
| 因果过度宣称 | 用 provenance 直接下"某经验有效"结论 | §5.2 的受控分配要求 |
| 信任洗白 | 注入内容携带指令或角色标记 | §5.3 的结构化渲染 |
| Context collapse | 反复重写上下文导致细节流失 | ACE 式增量 playbook，版本化条目 |
| 效率伪装 | 优化成本导致"少干活" | 成本只作约束 |
| **语料不足** | 统计设计建立在不存在的样本上 | 跟踪合格 TaskCase 增长速率；不足时改用小样本方法（见实施计划 §10.3） |

## 7. 实施顺序

顺序以 [自进化实施计划](./自进化实施计划.md) 的 G0～G7 为准：

```text
G0 信任与数据契约 → G1 受控重执行评测底座 → G2 只读 Shadow + L0
   → G3 Task Contract + Verifier → G4 State/Context/Recovery
   → G5 Experience/playbook/workflow → G6 Routing bandit → G7 窄任务权重训练
```

三点需要强调：

1. **两个 P0 可靠性机制（G3 / G4）排在 Experience 注入（G5）之前。** v1 把注入放在第三步是优化目标漂移——那会先建"经验进入 prompt"的闭环，再补"什么算完成"的信任底座，最容易把未经验证的产物扩散到后续轨迹。
2. **G5 的放行前置包含"失败簇证明该问题适合由外置知识解决"**，而不是"因为我们有 Reviewer 所以要用它"。
3. **不设产出配额。** 能有充分证据地得出"当前不应改"同样是成功。

**G0～G2 不涉及任何训练。** 真到 G7 再谈 RL 也不迟。
