日期：2026-08-27
范围：用户输入图片、工具返回图片、跨 provider 归一（GLM + DeepSeek）、成本与压缩治理
状态：设计方案，未实现

## 0. 结论先行

骨架已经在了，缺的是四处断链。`KernelMessage` 的 `ContentBlock` 联合类型早就包含 `ImageBlock`（`kernel/types/KernelMessage.ts:11,19`），`KernelSession.submitMessage` 早就接受 `string | Array<{type, ...}>`（`kernel/KernelSession.ts:243,353-358`），Anthropic 路径的 `MessageNormalizer` 是恒等透传（`kernel/messages/MessageNormalizer.ts:22`）。也就是说：**Claude / 走 Anthropic 协议的模型，理论上今天就能收图，只是没有任何代码路径会产生 image block。**

四处断链：

| # | 断链 | 位置 |
|---|---|---|
| 1 | OpenAI 协议出口显式丢弃图片 | `kernel/messages/DeepSeekMessageNormalizer.ts:105` — `// Silently skip image blocks` |
| 2 | 工具无法回传图片 | `core/types.ts:216` `ToolResult.content: string`；`kernel/tools/ToolExecution.ts:303-307` 把 `result.data` 无条件 `JSON.stringify` 成字符串。`KernelTool.ts:83-85` 的 `ContentBlockLike` 已经定义了 image 变体，但没有任何调用方用它 |
| 3 | 公共会话层全线 `string` | `routing/SessionRouter.ts:76`、`modes/MetaAgentSession.ts:260`、`modes/AgenticSession.ts:247`、`modes/CampaignSession.ts:192`、`cli/stream.ts:65,95` — 内核能收 blocks，但外面没有一条路把 blocks 递进去 |
| 4 | registry 无 vision 概念 | `providers/registry.ts` 的 `Capabilities` 只有 betas / thinking / reasoningEffort 三位，`resolveModelSpec` 只解析窗口与价格。运行时无法判断"这个模型收不收图"，误配只会拿到一个 400 |

已经就绪、**不需要改**的治理面（这是好消息，说明当初留了口子）：

- `MessageNormalizer.ts:101` `stripImagesFromMessages` — compact 请求前把 image 换成 `[image]`
- `kernel/compact/CompactPrompt.ts:819` — 摘要渲染时 `[image omitted]`
- `kernel/compact/StructuralTruncate.ts:61` — 截断时保留 image 不动
- `trajectory/privacy.ts:36` — 轨迹已对 `image` / `image_url` 做 sha256 脱敏，不落原始字节
- `kernel/api/DebugWriter.ts:202` — debug 输出 `🖼 [image omitted]`
- `kernel/messages/MessageFactory.ts:35-59` `makeToolResultMessage` 已经能收 `ContentBlock[]`

## 1. 两家接口的硬性要求

### 1.1 GLM-5.3-Flash（智谱）

- 原生多模态（GLM-5 系列首个），1M 上下文
- 图片参数：`messages[].content[]` 里加 `type: "image_url"` 块，通过 `image_url.url` 传**图片 URL（官方推荐）或 Base64 Data URL**；多图就多加几个 `image_url` 块
- 除图片外还支持视频、文件
- `thinking.type` 只支持 `enabled`（不能关思考），推荐 `temperature: 1`、`top_p: 0.95`、`reasoning_effort: max`
- 文档只描述了 **Chat Completion API（OpenAI 风格）** 的图片形状，**没有描述 Anthropic 兼容端点的图片形状** — 见 §3 未知量

### 1.2 deepseek-v4-flash-vision-exp

规格远比 GLM 文档明确，取两家交集时以它为准：

| 项 | 值 |
|---|---|
| 支持格式 | JPEG、PNG、GIF、WebP（**按文件实际内容判定，不看扩展名和声明的 MIME**） |
| 三种传法 | ① base64 data URL 内联 ② 外部 http(s) URL ③ Files API `file_id` |
| 外部 URL | ≤8192 字符，图片 ≤32 MiB，60 秒内下载完 |
| 请求体 | ≤48 MiB（内联 base64 计入） |
| 单图上限 | base64/URL ≤32 MiB；Files API `file_id` ≤64 MiB |
| 单请求图片数 | ≤600 |
| 单请求图片总大小 | 不含 `file_id` ≤64 MiB；含 `file_id` ≤200 MiB |
| 图片尺寸 | 单边 ≤8192 px；**单请求 ≥15 张时降为单边 ≤4096 px** |
| `detail` 字段 | `low`（推理前缩到 512×512）/ `high` / `original` / `auto`（当前等价 original） |
| Token 用量 | 入模前统一缩放到约 800×800 等效像素，**每图 token 上限 384**；2000×2000 和 5000×5000 消耗相同 |
| 位置限制 | **图片只能出现在 `user` 消息**，`system` / `assistant` 带图返回 400 |
| 模型限制 | 只有 vision 模型收图，其它模型返回 400 `This model does not support image` |

DeepSeek 另外提供 Anthropic 兼容端点 `https://api.deepseek.com/anthropic`，图片用 `image` 块 + `source.type: base64 | url | file`——与本仓 Anthropic 路径的形状完全一致。

### 1.3 对本仓架构的直接含义

本仓对 zhipu 走的是 **Anthropic 协议**（`registry.ts` zhipu 条目：`protocol: 'anthropic'`，`defaultBaseURL: 'https://open.bigmodel.cn/api/anthropic'`），对 deepseek 走的是 **OpenAI 协议**。而两家的图片文档都写在 OpenAI 风格上。所以：

- **DeepSeek 侧**：改 `DeepSeekMessageNormalizer`，把内部 image block 翻成 `image_url` 块。路径清晰，无未知量。
- **GLM 侧**：需要先实测 Anthropic-compat 端点收不收 `image` block。这是本方案唯一的架构分叉点，**必须先探针后写码**（§3）。

## 2. 分层方案

### L0 — 统一内部表示（不新增类型）

内部一律用 Anthropic 形状的 image block：

```ts
{ type: 'image', source: { type: 'base64', media_type: string, data: string } }
{ type: 'image', source: { type: 'url', url: string } }
```

理由：`KernelMessage` 已经是 Anthropic 形状，Anthropic 路径的 normalizer 是恒等透传，所以协议差异**只在 OpenAI 出口一处**收敛。反过来（内部用 OpenAI 形状）会让 Claude / GLM 两条主力路径都需要翻译。

新增 `src/kernel/messages/imageBlocks.ts`，**依赖叶子**（不 import `core/` 或 `kernel/` 的任何东西，与 `providers/registry.ts` 同样的约束，否则会被 `ArchitecturalInvariants.test.ts` 的循环检查拦下）：

```ts
export const SUPPORTED_IMAGE_MEDIA_TYPES = ['image/jpeg', 'image/png', 'image/gif', 'image/webp'] as const

/** 按 magic number 嗅探，不信扩展名 —— DeepSeek 明确按内容判定格式 */
export function sniffImageMediaType(bytes: Uint8Array): SupportedImageMediaType | null

export async function makeImageBlockFromFile(path: string): Promise<ImageBlock>
export function makeImageBlockFromUrl(url: string): ImageBlock
export function makeImageBlockFromBytes(bytes: Uint8Array): ImageBlock

/** 供 TokenEstimator 与预算用；按 provider 上限取常量，不做真实分词 */
export function estimateImageTokens(block: ImageBlock, ceiling: number): number

/** vision:false 的模型收到图时的兜底降级 */
export function downgradeImageBlock(block: ImageBlock, hint?: string): TextBlock
```

`sniffImageMediaType` 是刚性要求而非洁癖：DeepSeek 文档明写"格式由文件实际内容判断，而非文件名或声明的 MIME 类型"，一个被重命名为 `.png` 的 JPEG 会在服务端被接受但在我们这边算错 media_type，导致 Anthropic 路径 400。

### L1 — `providers/registry.ts`：能力位 + 限额表

`Capabilities` 增加一位：

```ts
export interface Capabilities {
  anthropicBetas: boolean
  anthropicThinkingParam: boolean
  reasoningEffort: boolean
  /** 模型是否接受图片输入。false 时入口拒绝，出口降级。 */
  vision: boolean
}
```

`ModelSpec` 增加可选限额（缺省取保守交集）：

```ts
export interface VisionLimits {
  maxImagesPerRequest: number
  maxImageBytes: number
  maxRequestImageBytes: number
  maxEdgePixels: number
  /** ≥ 这个张数时 maxEdgePixels 降档（DeepSeek: 15 张 → 4096） */
  edgeDowngradeAtCount?: number
  /** 能否直接传外链 URL（省 base64 体积） */
  acceptsImageUrl: boolean
  /** 单图 token 上限，用于 estimateContentTokens 与 AutoCostLedger */
  imageTokenCeiling: number
}
```

模型表补录：

```ts
// zhipu
'glm-5.3-flash': { contextWindow: 1_000_000, maxOutput: 131_072, pricing: GLM_STD,
                   capabilities: { vision: true }, vision: GLM_VISION_LIMITS },
'glm-5.3':       { ...现有, capabilities: { vision: true } },

// deepseek —— 注意只有这一款收图，其余带图直接 400
'deepseek-v4-flash-vision-exp': { contextWindow: 1_000_000, maxOutput: 131_072,
                                  pricing: DEEPSEEK_STD, capabilities: { vision: true },
                                  vision: DEEPSEEK_VISION_LIMITS },
```

家族规则（`MODEL_FAMILY_RULES`）配套调整，避免新版本又静默落到 `vision: false`：

- `glm`：major ≥ 5 且 minor ≥ 3 → `vision: true`（GLM-5.3 是首个原生多模态）
- `claude`：一律 `vision: true`
- `deepseek`：**保持 `vision: false`**。DeepSeek 的 vision 能力目前是单独一款实验模型，family 级别开 vision 会让 `deepseek-v4-pro` 带图直接吃 400

新增导出：

```ts
export function modelSupportsVision(model: string, baseURL?: string): boolean
export function getVisionLimits(model: string, baseURL?: string): VisionLimits
```

`CAP_ANTHROPIC` / `CAP_ZHIPU` 的 `vision` 默认值取决于 §3 探针结果；`CAP_DEEPSEEK` / `CAP_QWEN` 默认 `false`。

### L2 — 出口 normalizer

#### DeepSeekMessageNormalizer（主要改动）

`DeepSeekUserMessage.content` 从 `string` 放宽为 `string | DeepSeekContentPart[]`：

```ts
export type DeepSeekContentPart =
  | { type: 'text'; text: string }
  | { type: 'image_url'; image_url: { url: string; detail?: 'low' | 'high' | 'original' | 'auto' } }
```

规则：

1. **无图时保持纯字符串**。不要为了统一而把所有 user 消息都改成数组——那会把整个现有回归面重新拉一遍，收益为零。
2. base64 source → `data:${media_type};base64,${data}`；url source → 直接透传 url。
3. **assistant / system 消息上的 image 一律降级为文本占位**（`[image omitted]`）。DeepSeek 对此明确返回 400，这不是保守，是硬约束。
4. **`tool_result` 里的 image 需要拆分**：OpenAI 的 `role: 'tool'` 消息 content 只接受字符串，装不下图片。方案是发两条——先发 `{ role: 'tool', tool_call_id, content: '[见下一条 user 消息中的图片]' }`，紧跟一条 `{ role: 'user', content: [{text: '上述 tool_call <id> 返回的图片：'}, {image_url}] }`。这样既满足"图片只能在 user 消息"的限制，又保住了图片与工具调用的归属关系。
5. `detail` 缺省不填（等价 `original`）；未来若要省 token，在 L5 的老图淘汰里改填 `low` 而不是直接丢弃。

#### MessageNormalizer（Anthropic 路径）

保持恒等透传。只增加一个兜底：

```ts
/** vision:false 的模型收到图时降级，避免误配直接 400 */
export function downgradeImagesForModel(messages, supportsVision: boolean): KernelMessage[]
```

在 `KernelLoop` 组装请求前调用。正常路径应该在入口（L3）就拦住，这里是防御第二层——因为 `/model` 中途切模型是可能的，切到非 vision 模型时历史消息里还留着图。

### L3 — 入口：用户输入图片

#### 公共 API 签名放宽

```ts
export type PromptPart =
  | { type: 'text'; text: string }
  | { type: 'image'; source: ImageSource }

submit(prompt: string | PromptPart[]): AsyncGenerator<MetaAgentEvent>
```

`string` 重载保留，向后兼容。需要同步放宽的四层：`cli/stream.ts:65` `SteerHooks`/`submit` → `routing/SessionRouter.ts:76` → `modes/MetaAgentSession.ts:260` → `modes/AgenticSession.ts:247` / `modes/CampaignSession.ts:192` → `kernel/KernelSession.ts:243`（已支持，不用改）。

**关键陷阱**：`MetaAgentSession.ts:400`、`robotics/RoboticsSession.ts:1197`、`SessionRouter.ts:386` 都会构造 `effectivePrompt`（把上下文前缀拼到用户 prompt 前面）再往下传。这些地方必须改成"**前缀只拼到第一个 text part 上，image part 原样追加**"，绝不能对整个 prompt 做字符串拼接——否则图片会被 `String()` 成 `[object Object]`。

`extractUserGoalText`（`KernelSession.ts:600`）只取 text block，天然安全，不用改。

#### CLI 语法

推荐 `@` 前缀行内引用，兼容拖拽：

```
you › 这个报错什么原因 @/Users/x/Desktop/screenshot.png
you › 对比这两张图 @a.png @b.png
```

理由：repl 已有粘贴累加器（`cli/pasteAccumulator.ts`），终端拖拽文件会直接插入路径，`@` 前缀是最省事的路径。实现要点：

- 拖拽插入的路径常带引号（iTerm/Kitty 会给含空格的路径加单引号），需 strip
- `@` 后若不是可读的图片文件，**不要静默当普通文本**——提示"未找到文件"或"格式不支持"
- 非交互路径同时提供 `--image <path|url>`（可重复），供 `-p` 单轮与脚本使用

#### 入口校验（早失败）

在构造 blocks 时立刻校验，而不是等 API 返回 400：

- 目标模型 `vision === true`，否则报错并列出当前 provider 下可用的 vision 模型名
- media_type 在 `SUPPORTED_IMAGE_MEDIA_TYPES` 内（按 magic number）
- 张数 / 单图字节 / 总字节 / 单边像素 不超过 `getVisionLimits()`，含 15 张降档规则
- 超限时给出可执行的建议（"压缩后重试"/"改用外链 URL"），不静默丢图

### L4 — 工具返回图片

`ToolResult.content` **保持 `string` 不动**（第三方工具源码兼容是 `core/types.ts:219` 注释里写死的承诺），新增可选字段：

```ts
export interface ToolResult {
  content: string           // 不变；无图工具完全不受影响
  isError: boolean
  /** 富内容块。存在时 content 作为纯文本回退（debug / 轨迹 / compact 摘要用） */
  blocks?: ContentBlockLike[]
  ...
}
```

`kernel/tools/ToolExecution.ts:303-307` 改为：有 `blocks` 就构造 `ContentBlock[]` 交给 `makeToolResultMessage`（它已经能收数组，见 `MessageFactory.ts:35-59`），否则走现有 string 路径。

`tool.maxResultSizeChars` 的截断**只作用于文本块**，图片块单独按字节配额裁（超配额时丢最早的图，保留文本说明）。

首批接入：

- **`read_file`**：`.png/.jpg/.jpeg/.gif/.webp` 走 image block。现在这些文件会被 `readFile(path, 'utf-8')` 读成乱码（`tools/fs/read_file/index.ts:74`），属于纯粹的 bug 修复
- **`web_fetch`**：`content-type: image/*` 时返回 image block。现有注释（`tools/network/web_fetch/index.ts:120`）已经承认"抓 PDF/图片会被当 UTF-8"
- bash 截图暂不接入（涉及平台差异，等 P3 之后单独评估）

权限模型不变：图片读取走现有 `read` category + workspace jail，不需要新增 permission 类别。

### L5 — 成本与压缩治理

这一层不做，前四层上线当天就会出事。

#### 5.1 token 估算

`context/TokenEstimator.ts:17` 的 `estimateTokens(text)` 只吃字符串。新增：

```ts
export function estimateContentTokens(blocks: ContentBlock[], imageTokenCeiling: number): number
```

图片按 provider 的 `imageTokenCeiling` 计常量（DeepSeek 明确 384；GLM 未公布，探针出来前按 1600 保守估）。

**这是必做项而非优化**：一张 1 MB 的图 base64 后约 1.4 M 字符，按 4 字符/token 会被算成 ~350k token，直接把 auto-compact 触发线（`glm-5.2` 是有效窗口的 65%）打穿，导致每贴一张图就触发一次全量压缩。

#### 5.2 会话持久化不能落 base64

`core/SessionStore.ts` 的 JSONL 每条消息原样序列化（`SessionStore.ts:121-133`），一次贴图就能让 session 文件涨到几十 MB，并且让 `META_AGENT_MAX_RESUME_MESSAGES` 的消息数上限彻底失效（数量对了但体积爆了）。

仿照已有的 `stripThinkingForStorage`（`SessionStore.ts:112`）加一道：

```ts
function externalizeImagesForStorage(message: ConversationMessage): ConversationMessage
```

- 图片字节写到 `~/.meta-agent/sessions/<sessionId>/blobs/<sha256>.<ext>`
- 消息里存 `{ type: 'image', source: { type: 'file_ref', sha256, media_type, bytes } }`
- resume 时按 sha256 回填；blob 缺失则降级成 `[image: 已清理]` 文本，不让 resume 失败
- 会话删除时连带清理 blobs 目录

#### 5.3 老图淘汰

图片是纯输入成本，且不会被 prompt cache 的收益覆盖（本仓目前不发 `cache_control`，Zhipu 是隐式前缀缓存——见 `registry.ts` 的 `CAP_ZHIPU` 注释）。规则：

- 只有最近 N 轮（默认 2，`META_AGENT_IMAGE_RETAIN_TURNS` 可调）的图片保持原样
- 更早的降级为 `[image: <文件名或工具来源>]` 文本
- 中间档可选：降级前先把 `detail` 改成 `low`（DeepSeek 支持，512×512）

compact 侧不用动——`stripImagesFromMessages` 已经在压缩请求前把图换成 `[image]`（`MessageNormalizer.ts:101`），`CompactPrompt.ts:819` 也已处理。

## 3. 未知量与探针（写代码之前必须实测）

方案里有三个不能靠读文档确定的点。仿照已有先例（`registry.ts` 里 `scripts/probe-glm-cache.mjs` 的实测结论直接写进了注释），先写 `scripts/probe-vision.mjs`，输出一张能力矩阵再动主干代码。

**① 智谱 Anthropic-compat 端点收不收 `image` block？** —— 最大分叉点

对 `https://open.bigmodel.cn/api/anthropic` 分别发 `source.type: base64` 和 `source.type: url` 两种。

- 收 → 本方案 L2 的 GLM 侧零改动，皆大欢喜
- 不收 → 三个备选：(a) zhipu 的 `protocol` 按模型分流，vision 模型走 openai 协议；(b) 仅带图请求切到 `https://open.bigmodel.cn/api/paas/v4`；(c) 在 `registry.ts` 引入 `visionProtocol` 独立于主 protocol。倾向 (a)，因为它把差异留在 registry 这个单一真相源里，不引入第二套 baseURL 逻辑

**② deepseek-v4-flash-vision-exp 支不支持 tool_calls？**

本仓的 loop 强依赖工具调用。若这款实验模型不支持工具，它就只能进 `models.flash`（compact / mode-detect / 侧调用）而不能当主模型，`registry.ts` 的条目要相应标注。

**③ GLM-5.3-Flash 的图片计费口径**

用于 `estimateContentTokens` 的常量与 `AutoCostLedger`。实测方式：发一张已知尺寸的图，读 response 的 `usage.input_tokens` 差值。

## 4. 分阶段落地

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P0** | 探针脚本 + registry 能力位/限额表 + `imageBlocks.ts` + DeepSeek normalizer 出图 | `examples/` 下一个脚本，对 GLM 与 DeepSeek 各发一张 PNG，都能拿到正确描述 |
| **P1** | `submit` 签名放宽（五层）+ CLI `@image` 语法 + 入口校验 | `meta-agent -p "这张图什么内容 @a.png"` 走通；非 vision 模型给出清晰报错而非 400 |
| **P2** | `ToolResult.blocks` + `read_file` / `web_fetch` 出图 | 模型自己调 `read_file` 读一张截图并描述内容 |
| **P3** | token 估算 + 持久化外置 + 老图淘汰 | 连贴 10 张图后 session 文件 < 1 MB；auto-compact 不被误触发；resume 后图片可回填 |

P0 与 P1 之间没有强依赖，但 P1 依赖 P0 的 registry 能力位做入口校验，顺序不要倒。

## 6. 明确不做

- **视频 / 音频**：GLM 文档提到支持视频和文件，但两家接口形状差异大（DeepSeek 的 vision 文档只讲图片），等 P3 之后单独立项
- **DeepSeek Files API（`file_id` 复用）**：只有当"同一张图跨多轮反复上传"成为实测瓶颈时才值得。P3 的老图淘汰会先把这个压力消掉大半，届时再评估
- **图片生成**：本方案只做理解侧输入，不涉及出图
- **prompt cache 显式断点**：与多模态正交，`registry.ts` 里已有的那段注释说明了为什么现在不做，本方案不改变该结论
