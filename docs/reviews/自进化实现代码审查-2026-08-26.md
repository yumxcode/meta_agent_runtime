## 2. 已确认并修复的缺陷

### 2.1 [P1] evaluator bundle 加载失败被报成「候选正常失败」

**位置**：`EvalRunner.finish()`

`loadEvaluatorBundle` 抛错时 `bundle` 为 undefined，`skippedChecks(undefined)` 返回 `[]`。而 `inconclusive` 由 `checks.some(...)` 计算——空数组为 `false`。实测：

```
checks=[] succeeded=false inconclusive=false
```

即「什么都没评测」被报告为「候选失败了」。这正是该模块整体设计要防的 fail-closed 违反，且它会一路传播进指标（见 2.2）。

**根因是我自己的测试编码了这个 bug**：原测试只断言 `succeeded === false`，没断言 `inconclusive`，于是缺陷通过了验收。

**修复**：`checks.length === 0` 一律视为 inconclusive——没有检查就是没有证据，无论什么原因。回归测试已补断言。

### 2.2 [P1] 零 criteria 的用例被计入 `case_success_rate` 分母

**位置**：`Metrics.isConclusive()`

原实现只判 `unresolvedCriteria === 0`。上一条产生的报告（三类计数全为 0）因此满足「已判定」，且 `isSuccess` 为 false，实测：

```
conclusiveCases=1  caseSuccessRate=0  caseInconclusiveRate=0
```

一次基础设施故障被记成一次质量退化——正是[指标契约](../知识系统/评测指标与统计契约.md) §1 明令禁止的分母错误。

**修复**：`isConclusive` 追加「至少有一条 criterion 得到判定」。与 2.1 是两层独立防线，因为 Metrics 可以脱离 EvalRunner 单独使用。

### 2.3 [P2] `bundleOutsideWorkspace` 声称了一个不可能触发的检查

**位置**：`EvalRunner` setup 阶段 + `IsolationReport`

`assertBundleOutsideWorkspace(bundleDir, restoreTarget)` 中 `restoreTarget` 是 `mkdtemp` 新建目录下的子目录。**任何调用方传入的既存路径都不可能位于其中**，实测四种 bundleDir（含把 bundle 指向 workRoot 本身）检查均不触发。

因此 `isolation.bundleOutsideWorkspace: true` 是一个未挣得的声明，而这是我对外宣称的五道防线之一。

**同时暴露一条空洞测试**：「refuses to run when the bundle sits inside the workspace」通过的真实原因是 bundle manifest 不存在（`loadEvaluatorBundle` 先执行），与容器检查无关。

**修复**：保留 guard 作为纵深防御（未来若支持显式 workspace 路径即可生效），但在类型注释中如实写明「由构造保证，非由检查保证，真正起作用的是 `bundleHashVerified`」；容器检查改为直接单测覆盖。

## 3. 未修复的发现（需要决策）

### 3.1 [P2] gitBase 探测在每个 run 的关键路径上

`KernelSession.submitMessage` 每次调用都执行 `git rev-parse` + `git status --porcelain`。本仓库实测 **222ms**。

放大因素：

- 每个 **run** 一次，不是每会话一次；
- 子代理经 `MetaAgentSession → AgenticSession → KernelSession`，**各自独立探测**，并发子代理会并发打同一个仓库；
- 超时上限 3s，大仓库上 `git status` 可能接近该上限。

已做的缓解：非 trajectory 模式完全跳过；三次 git 调用已合并为两次。

**可选方案**：(a) 不 await，就绪则附加、未就绪则留空；(b) 子代理不探测，复用父会话的 base；(c) 维持现状并接受成本。**建议 (a)**——gitBase 是尽力而为的记录，不值得挡在首 token 前面。

### 3.2 [P3] `caseClaimedSuccess` 在多轨迹 case 上语义可议

`src/cli/commands/reviewer.ts` 用「任一 member 的 `lastOutcome === 'success'`」判定 agent 是否宣称完成。一个根轨迹 parked、子代理 success 的 case 会被算作「宣称完成」。这会直接影响 T3 false-success 的分子。建议改为只看根轨迹的最终 outcome，但需要先看真实数据分布再定。

### 3.3 [P3] 四个模块仍无生产调用方

`computeMetrics` / `comparePaired` / `runEvalCase` / `captureBaseSnapshot` 生产调用方为 0（`renderInjectionBlock` 为 0 是设计如此）。它们卡在「没有真实评测集」上，属于计划 §11 点名的镀金风险。不建议再扩建，建议先产出数据。

## 5. 方法论结论

三个缺陷有一个共同形态：**防线写好了，但从未被真正触发过，而测试恰好也没要求它触发**。

- 2.1：测试没断言 `inconclusive`；
- 2.3：测试因另一个原因通过；
- 上一轮 §15.11 的角色标记检查：折叠先于校验，正则永不命中。

在此之前引入的「故意破坏验证」（拿掉防线看测试是否失败）能抓住第三类，但抓不住前两类——因为**破坏一个本就不可达的检查，测试当然不会变化**。

> 补充判据：对每条声称的防线，除了问「拿掉它测试会不会失败」，还要问「在真实调用路径上，什么输入能让它触发」。答不上来的，它就不是防线。
