## 2. 缺陷

### M-1（严重）web_fetch 静默内联被截断的图像

**位置**：`src/tools/network/web_fetch/index.ts`

图像分支声明 `MAX_IMAGE_BYTES = 5 MiB`，但传输层在 `MAX_CONTENT * 2 = 200 KiB` 处就 `res.destroy()` 停止接收。两个上限相差 25 倍，且**较小的那个先生效**，所以 5 MiB 这个数字从来没有可达过。

后果不是"大图失败"，而是**静默的错误答案**：

- 魔数位于偏移 0，所以被截断的 body 仍然通过 `sniffImageMediaType()`；
- 200 KiB 远小于 5 MiB，所以也通过尺寸检查；
- PNG 的 IHDR 在前 24 字节内，所以 `readImageDimensions()` 报告的是**原图**尺寸。

于是任何超过 200 KiB 的网络图像都会被内联为半张图，并被描述成一张完整的 `1920×1080` PNG。模型和用户都没有任何线索。

实测复现（修复前的代码路径）：

```text
original bytes : 614400
delivered bytes: 196608
under 5MiB image cap?  true → passes the size check
sniffs as PNG?         true → passes the format check
=> [image: …/photo.png (image/png, 1920×1080, 204800 bytes)]
```

**修复**：

1. `PinnedResponse` 增加 `truncated: boolean`。文本调用方不需要它（本来就会截断显示并注明），图像调用方必须有它。
2. 按 content-type 给图像响应单独的传输预算（`MAX_IMAGE_BYTES`），让声明的上限真正可达。
3. **截断检查排在格式嗅探之前**。顺序是有意义的：先嗅探会报"不是支持的图像格式"，而格式本来是好的，坏的是下载 —— 那是个既错误又误导的诊断。
4. 图像分支抽出为导出的 `renderImageResponse()`。SSRF 守卫按设计拒绝 loopback，该分支无法端到端驱动，这与 `classifyBody` / `renderPage` 已被导出的原因相同。

**回归测试**：`webFetchImages.test.ts` 9 例。已实测：其中 3 例对修复前代码失败、对修复后通过。

### M-2（中）附件在校验尺寸之前就被完整读入

**位置**：`src/cli/attachments.ts`

`loadAttachment()` 调用 `stat()` 拿到 `size`，但只用它判断 `size === 0`，随后 `makeImageBlockFromFile()` 无条件读取整个文件并 base64 编码（体积再涨 33%）。尺寸上限直到 `validateAttachments()` 才检查 —— 那时内存已经付过了。

`@/path/to/huge.png` 指向一个多 GB 文件时，进程会在"本该拒绝它"的那个校验运行之前就耗尽内存。

**修复**：`loadAttachment()` 接受可选 `maxBytes`，在 `stat` 尺寸上就拒绝。`buildPromptInput()` 在读取任何文件之前先解析目标模型的 `maxImageBytes` 作为上限。`validateAttachments()` 的检查保留 —— 这只是让昂贵路径有界的前置过滤，不是替代。

**回归测试**：4 例。已实测对修复前代码失败。

### M-3（中）公开入口导出了签名却没导出满足它的手段

**位置**：`src/index.ts`

`MetaAgentSession.query()` 的参数类型是 `PromptInput`，可以携带图像。但 `PromptInput`、`PromptPart`、`PromptImagePart`，以及任何构造图像块的函数，都没有从 `src/index.ts` 导出。

`package.json` 的 `exports` 只映射 `.` → `dist/index.js`，所以包的消费者**只能**看到这个文件。实际效果是：SDK 用户能看到一个接受图像的签名，却既无法命名那个类型，也无法在没有深入 `dist/` 内部路径的情况下构造一个合法的图像部分。

这正是 `PublicEntrySurface.test.ts` 的 docstring 记录过的那次事故的重演 —— v0.9.0 的工具新增导出到了 `tools/index.ts`，仓库内每个测试都用得好好的，装成 tarball 才发现包里根本没有。

**修复**：从入口导出 `PromptInput` 系列类型与函数、`imageBlocks` 的构造与检查函数、以及 `modelSupportsVision` / `getVisionLimits` / `effectiveEdgePixels`（让调用方在付出上传成本之前就能判断目标模型是否接受图像）。

同时把这批名字加进 `PublicEntrySurface.test.ts` 的 `PUBLIC_VALUES`，并补上 8-27 评审新增的 store-id 那批 —— 它们此前也没进契约。

**验证**：装 tarball 到干净工程，确认 15 个导出全部可达，并跑通一次完整的"构造图像 prompt → 提取文本 → 加前缀保留图像"流程。

## 3. 确认无问题的部分

| 项 | 结论 |
| --- | --- |
| `read_file` 图像分支 | `MAX_READ_BYTES` 5 MiB 检查在图像分支**之前**，有界 |
| 格式判定 | 一律字节嗅探，不信任扩展名与声明 MIME —— 与 DeepSeek 行为一致，也避免了改名文件在 Anthropic 侧变成 400 |
| `estimateImageTokens` | 固定 ceiling 而非 chars/4。两个错误答案（按字符估算会把 1 MB 图算成 ~350k token；跳过图像块会算成 0）都被显式避开并写在注释里 |
| `applyImageRetention` | 从后向前遍历，"最近"在任何改写发生前就已确定；`tool_result` 内嵌图像同样计数 |
| `META_AGENT_IMAGE_RETAIN` | 走 `readIntEnvOr`，自动继承 8-27 评审的严格解析修复 |
| 新增 env var | 已登记进 `ENV_REGISTRY` |
| WebP 尺寸解析 | VP8/VP8X/VP8L 三种容器都处理，位域偏移正确 |
| JPEG SOF 扫描 | 正确排除了共用 0xc0-0xcf 区间的 DHT/DNL/DAC |
